Go 分配与 GC：逃逸、引用保留和内存预算 ​

前置是切片共享、指针和值复制与基础测试。内存上涨有两种常见成因：不断创建短命对象，或者已有对象一直被引用。前者增加分配和回收工作，后者抬高每一轮回收后仍需保存的内存。两者可以同时发生，检查的指标各不相同。

栈、堆与可达性 ​

局部变量可以被移到堆上，new(T) 得到的对象也可以放在栈上。编译器根据生命周期、大小和优化作出选择。返回局部变量的地址是安全的，编译器须让对象活到最后一个使用者不再需要它。内联改变调用上下文，因此某个源码位置在一次构建的逃逸结果不能概括所有构建。

进入仓库的 examples/go/system-lab，用 go test -gcflags=-m=2 . 查看诊断中的 escape、moved to heap 与 inline。再执行 go test -run '^$' -bench 'Benchmark(Format|Append)$' -benchmem -count=5 .，观察每次操作平均分配的次数 allocs/op 和字节数 B/op。源码诊断解释编译决策，基准反映该输入的运行成本。两种格式化实现

Go 的堆回收按可达性工作。运行时由 goroutine 栈、全局变量等根出发，沿引用确定仍可使用的对象。并发标记期间，写屏障帮助保持标记正确；应用分配还可能承担辅助标记的 CPU 成本。不可达对象的存储可逐步回收并复用。高分配率可能让每个对象都活不久却频繁触发 GC；巨大的可达对象则可以在很少新增分配时维持高活堆。

同条件比较保留与复制 ​

实验每组都创建 8 个 1 MiB 缓冲区，各保留一个字节直到测量结束。两组使用相同的数据、次数和 GC 时机，只改变这个字节是否复制到独立切片。runtime.GC() 限定本次测量发生在强制回收之后，runtime.KeepAlive 让当前组的 8 个结果在读取指标前一直可达。每次调用返回后该组的引用就不再保存。

go
package main

import (
	"fmt"
	"runtime"
)

func heapAfterGC(copyByte bool) uint64 {
	kept := make([][]byte, 0, 8)
	for i := 0; i < 8; i++ {
		buf := make([]byte, 1<<20)
		buf[0] = byte(i)
		one := buf[:1:1]
		if copyByte {
			one = append([]byte(nil), one...)
		}
		kept = append(kept, one)
	}
	runtime.GC()
	var stats runtime.MemStats
	runtime.ReadMemStats(&stats)
	runtime.KeepAlive(kept)
	return stats.HeapAlloc
}

func main() {
	views := heapAfterGC(false)
	copies := heapAfterGC(true)
	fmt.Println("保留组多出至少 6 MiB", views >= copies && views-copies >= 6<<20)
}

在独立模块保存为 main.go，执行 go run .。预期结果是两组相差接近 8 MiB，示例用宽于噪声的阈值显示观察是否吻合。

保留组从 kept 经切片指针仍可达所有大数组。[:1:1] 使长度和容量都为 1，底层对象依旧是原数组。复制组的 kept 只指向 8 个独立的小结果，大数组已失去最后一个引用。验证时可以在两次测量后打印 views 和 copies，交换两组顺序再运行。HeapAlloc 是该进程的堆分配状态，还包含程序自身其他在用对象，所以差值无需恰好等于 8 MiB。显式 GC 在这里服务于对照测量，业务路径无需照搬。

同一台 Windows amd64 机器运行 Go 1.27.2 时，先测保留组得到 8,951,024 字节，复制组得到 562,480 字节。另起进程交换测量顺序，复制组为 562,624 字节，保留组为 8,956,360 字节。两次相差均约 8 MiB，可用来对照底层数组的总大小。

在业务中，heap profile 的 inuse_space 说明采样到的活对象占用，alloc_space 显示累计分配。对象回收后，运行时可先保留空闲页供后续分配，操作系统也有自己的回收节奏，所以 RSS 可能稍后才下降。若活堆随请求数持续增长，应追查缓存、队列和仍在工作的 goroutine 持有的引用。若活堆稳定而 RSS 上升，再检查空闲页、外部库分配与映射。内存 profile 的读法

GOGC 与 GOMEMLIMIT 各控制什么 ​

GOGC 调整堆增长与 GC 频率的取舍。用官方 GC 指南的简化模型，在软限制没有压低目标时，下一轮目标堆约为 上轮活堆 + (上轮活堆 + GC 根集合大小) × GOGC / 100。若活堆 8 MiB，根集合 2 MiB，GOGC 为 100 时目标约 18 MiB；改为 50 时约 13 MiB。存活规模与分配速率不变时，允许的新分配空间变小，标记通常会更频繁。这个数用于解释堆目标，进程 RSS 还有代码映射和其他组成。

GOMEMLIMIT 或 debug.SetMemoryLimit 给 Go 运行时管理的内存设置软预算。运行时参照的量大致是 MemStats.Sys - MemStats.HeapReleased；外部库和某些映射还会额外使用进程内存。若存活数据已经接近预算，更积极的 GC 能腾出的空间有限，还可能拖慢应用。运行时可以超过软限制以维持进展。容器应给外部占用预留余量。GOGC=off 也不取消独立设置的软限制。

先固定输入、工具链、并行度和运行时长。在 examples/go/system-lab 下，按表分别以独立进程运行同一基准，每组重复五次。PowerShell 可在新开的实验终端给 $env:GOGC、$env:GOMEMLIMIT 赋表中两项，完成后关闭该终端。Bash 可用 GOGC=100 GOMEMLIMIT=128MiB 前缀只为本次基线命令设置环境。

在上述 Windows 实验环境，三组各五次测量均得到 32 B/op 和 1 allocs/op。这些指标描述每次格式化创建的结果，无法单独判断预算是否触及。要判断软限制的影响，应观察目标堆、活堆、周期数和 GC CPU，可用 runtime/metrics 采集；服务级取舍再结合吞吐、尾延迟和容器占用判断。sync.Pool 中的临时对象可在 GC 时被丢弃，不能用来维持缓存容量或管理文件、连接等需明确关闭的资源。

练习与自检 ​

如果保留组改为 buf[:1]，哪项可观测结果可能变化？若服务两版每请求分配相同字节，回收后存活堆却持续分化，应该优先查哪条证据？

参考解法

切片容量从 1 变成整个数组的容量，保留的底层数组大小并未改变。每次分配记录的是创建速率，GC 后仍存活的对象反映生命周期。先按活对象类型和分配栈确定是什么占了空间，再追查持有这些对象的长期缓存、队列或 goroutine。
