Go 并发入门：goroutine、channel 与共享状态 ​

前置是函数与闭包。启动一项后台计算时，要先决定结果交给谁、谁能宣布不会再有结果，以及调用方怎样知道已经完成。并发使不同任务可以交错推进，即使只有一个可用的执行资源，这些协议仍然必要。

启动、交接与完成 ​

go f(x) 先在调用者处求出函数和实参，再启动 goroutine 来执行函数体。调用者随后继续，main 返回时进程结束。若后台工作决定程序结果，必须用通信或等待原语建立一个明确的完成点。

channel 是带元素类型的通信通道。无缓冲通道让发送者和接收者在交接值时同步。带缓冲通道允许先发送，直到缓冲区满；一次成功发送只说明值已交接或进入缓冲区。消费者对该值的业务处理是否结束，需要另外的完成协议。

go
package main

import "fmt"

func main() {
	result := make(chan int)
	go func() {
		result <- 2 + 3
		close(result)
	}()
	value, ok := <-result
	fmt.Println(value, ok)
	value, ok = <-result
	fmt.Println(value, ok)
}

预期输出

text
5 true
0 false

第一次接收取走一个真实元素，第二次在通道已经关闭且数据耗尽时返回元素零值与 false。即使发送的值本来就是 0，成功接收的 ok 仍为真。for v := range ch 使用同样的结束条件，缓冲中的元素会先被读完。

知道全体发送者已结束的一方负责关闭。发送到已关闭通道或重复关闭会 panic；一个活着却没有发送者的未关闭通道，会让接收者继续等。未初始化的 nil 通道收发都永久阻塞，在 select 中可利用这一点禁用相应分支。仅交接一个结果并等到它时，也可以约定只接收一次，无须为了回收内存而关闭。

共享状态与数据竞争 ​

两个 goroutine 都访问一个普通变量，其中至少一个执行写入，又没有把访问排定先后，就可能发生数据竞争。count++ 包含读、计算和写回，两个工作者可能读到同一个旧值。可以让一个 goroutine 持有计数并从通道接收增量；如果多个工作者必须直接访问它，则让每次相关读写使用同一把 sync.Mutex。把两次写都放进临界区还能使所有读取遵守同一契约。

sync.WaitGroup 负责等一组工作结束。传统写法先 Add 登记，再启动 goroutine，其中在完成时 Done，调用方 Wait。等待能使完成后的读取看到结果，仍无法将两个工作者内部的 count++ 排成先后。这是“完成通知”和“保护更新”的具体区别。Go 1.25 起也可用 WaitGroup.Go 启动适合其契约的任务。同步工具与共享不变量

练习与自检 ​

不运行阻塞反例，先推导若去掉 close(result)，哪一行能完成？若改用容量 1，答案会变吗？一个计数程序只在打印前 Wait，它还应该在哪里同步？

参考解法

第一次仍能收到 5。第二次接收没有值，也没有关闭信号，容量 1 只改变首次发送的等待条件。计数程序还须保护工作者之间每一次更新以及并发读取。完成协议规定何时可以读最终结果。
