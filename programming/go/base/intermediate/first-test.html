Go 第一条测试：用可观测结果验证行为 ​

前置是包和模块。测试用程序可观察的结果描述契约。先定输入和预期，再编写实现，可以避免把同一处误解同时复制进代码和断言。

从一个可反驳的预期开始 ​

我们约定 Sum 接受任意整数切片，返回所有元素之和，空输入返回 0。本例选用不会溢出的输入。只测一个正整数难以区分“逐个累加”和“取最后一个数”。[1,2,3] 能区分两者，含负数的输入检查方向，空输入检查初始值与零轮循环。

在空目录执行 go mod init example.com/study，保存这两个文件。测试与被测函数属于同一个包，_test.go 只参加测试构建。测试函数接受 *testing.T，可以在失败时报告用例名、输入、实际值和预期值。

sum.go

go
package study

func Sum(values []int) int {
	total := 0
	for _, value := range values {
		total += value
	}
	return total
}

sum_test.go

go
package study

import "testing"

func TestSum(t *testing.T) {
	cases := []struct {
		name  string
		input []int
		want  int
	}{
		{"empty", nil, 0},
		{"positive", []int{1, 2, 3}, 6},
		{"negative", []int{-3, 1}, -2},
	}
	for _, tc := range cases {
		t.Run(tc.name, func(t *testing.T) {
			if got := Sum(tc.input); got != tc.want {
				t.Fatalf("Sum(%v) = %d, want %d", tc.input, got, tc.want)
			}
		})
	}
}

在该目录执行 go test -v .，预期三个子测试均通过。表中的预期是人工推算的独立数据；若用被测函数再算一遍预期，即使实现错了，两边也会同时得到相同错值。

由一次失败确认断言有效 ​

临时将 total += value 改作 total = value。运行 go test -run TestSum/positive -count=1 .，预期测试失败，显示得到 3、预期 6。恢复累加逻辑，再用 go test ./... 检查当前模块下的包。一次能变红也能恢复的实验，比单看通过次数更能说明这项测试保护哪种行为。

-run 缩小测试范围，-count=1 跳过成功结果缓存。读失败报告时，先确认具体输入和出错层次，再跟踪产生实际值的那一步。测试通过只说明已经选择的样例符合预期；输入越界、不同调用互相干扰，或并发行为要有相应测试才能观察。测试隔离、基准与失败定位

练习与自检 ​

增加 [5,-5] 和 []int{}。两者的预期相同，它们能暴露哪些不同错误？原来的空输入用的是 nil，如果调用者也传一个长度为零的已初始化切片，会怎样？

参考解法

两组都得 0。前者检查正负数相消，后者没有循环迭代，检查初始化与空输入约定。nil 与已初始化的空切片都能零次遍历。若业务要求区分两种输入，则需要另定契约和独立断言。
