Go 协作取消：停止信号与等待退出 ​

前置是channel 的发送与关闭。如果消费者只取两个值就离开，生产者可能已经准备发送第三个值。要让函数能返回，得为这个阻塞点安排一条退出路径。

通知取消与确认退出 ​

context.WithCancel 建立一个派生上下文。调用 cancel 后，ctx.Done() 关闭，等待它的多个 goroutine 都能观察到信号。cancel 返回的时刻并不说明工作者已经执行收尾；是否退出，由工作者发出的完成通知确认。父上下文取消会向派生上下文传播；子任务取消自身不会自动取消父任务。

下列生成器对外返回两个只读通道。out 交付数据，发送者在退出时关闭它。done 确认退出；后登记的 defer close(out) 先执行，观察到 done 关闭时，输出通道已关闭。对于只需排空输出的调用者，也可选择约定一个输出通道并读至关闭。

go
package main

import (
	"context"
	"fmt"
)

func numbers(ctx context.Context) (<-chan int, <-chan struct{}) {
	out := make(chan int)
	done := make(chan struct{})
	go func() {
		defer close(done)
		defer close(out)
		for n := 1; ; n++ {
			select {
			case out <- n:
			case <-ctx.Done():
				return
			}
		}
	}()
	return out, done
}

func main() {
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()
	out, done := numbers(ctx)
	fmt.Println(<-out, <-out)
	cancel()
	<-done
	fmt.Println(ctx.Err())
}

预期输出

text
1 2
context canceled

接收方离开后，无缓冲通道的下一次发送无法完成，取消分支却已就绪，生产者因此能返回。仅在发送语句之前检查一次 ctx.Err() 会留下一个窗口，如果检查后发送永远阻塞，工作者就无法再检查。缓冲能推迟塞满的时间，不能独自建立退出条件。

若发送与取消两个分支都就绪，select 可以选择其中任一个，不保证取消优先。要求“调用方返回后再也不会发生写入”时，除了通知取消，还要等待负责写入的工作者退出。若工作者在执行第三方 I/O，也要把 context 或可中断的超时传给实际调用；外层监听通道无法停止一个永远不返回的同步函数。

期限和测试 ​

context.WithTimeout 和 WithDeadline 使调用链共享一个时间预算。拥有派生上下文的一方仍应在工作提前结束时调用 cancel，及时释放定时器等资源。ctx.Err() 可区分主动取消与期限到期。context 适合传递请求范围的取消、期限与元数据。

测试退出协议时，先读一个正常结果，再取消并等待 done。可以用 select 在 done 和测试的超时上限之间选择：收到完成信号即通过，超时才报告未退出。固定 Sleep 只等时间经过，会让慢机器偶发失败，也可能让泄漏的工作者逃过断言。

练习与自检 ​

假设输入目前没有消费者，取消前工作者可能阻塞在哪里？若去掉发送分支所在的 select，调用方会停在哪一步？正常例子只取一个值后取消，最后应看到什么？

参考解法

生产者可阻塞在发送或等待调度。发送和 Done 同时参与选择时，消费者离开后取消能让它返回。改成单独的阻塞发送会让调用方在 <-done 等不到确认。正常例子只读一个数会得到 1，再观察到 context canceled。
