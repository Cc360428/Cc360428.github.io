Go 开发工具：用 VS Code 定位工作目录与断点问题 ​

前置：工具链与模块工作区。用编辑器启动 Go 程序时，目标包、进程工作目录、命令行参数是三个独立输入。断点能命中只说明执行走到这一行；相对文件路径找错还需核对该进程的 cwd。

在同一入口切换 cwd ​

在 VS Code 打开仓库的 examples/go/foundations，其中 task-cli 是 main 包。下面的 program 固定这个入口，cwd 则决定程序从哪里解释相对路径。程序默认读取 tasks.json，也允许用 TASKS_FILE 指定其他路径。下文保留默认文件名。

json
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Task CLI · module cwd",
      "type": "go",
      "request": "launch",
      "mode": "debug",
      "program": "${workspaceFolder}/task-cli",
      "cwd": "${workspaceFolder}",
      "args": ["list"]
    }
  ]
}

在 task-cli/main.go 的 os.ReadFile(file) 处设断点。复制同一个配置，保留 program 和 args，把第二份 cwd 改为 ${workspaceFolder}/task-cli。假设只有模块根的 tasks.json 含任务 1，且两个目录都没有改变默认文件名的环境配置：

配置仍执行哪个包实际读的文件可观察结果
cwd 为模块根task-cli模块根/tasks.json显示任务 1
cwd 为 task-cli同一个 task-cli模块根/task-cli/tasks.json文件缺失时按空列表处理

若两个路径都已有文件，输出取决于各自内容。可从包含 Go 源码的模块根构建一次二进制，再用两个新的临时目录分别启动相同绝对路径的二进制：只在第一个目录执行 add，随后分别执行 list。这样能用命令行复现工作目录条件，避免将 IO 问题归给调试器。

断点不命中如何分层 ​

先在模块根执行 go test ./task-cli 检查源代码能否编译，再以调试配置指定的入口和参数运行。若目标没有构建成功，调试器就没有可启动的程序。编译通过而断点为空心，检查 Delve 输出、实际程序与源码是否为同一构建以及这条分支能否执行。断点已命中但数据不同，查看 file、args、工作目录和环境；工具安装无法改变应用选的是哪个文件。

mode: "test" 用于测试包，request: "attach" 用于已有进程。调试不了解来源的多进程问题时，先为每个进程单独确认入口和端口，再组合会话。Go 扩展调试说明

注释与文档 ​

导出 API 的约束、失败语义和并发性写在编码规范；发现可复现的行为用测试与 Example保存。

练习与自检 ​

如果第二份配置把 program 也改成模块根，预期是启动失败，还是成功运行但读到另一份文件？

参考解法

模块根没有可启动的 main 包，程序尚未运行。先还原 program，再单独改 cwd，此时才会得到运行成功但数据路径不同的结果。

命令行能检查这里的文件选择行为；编辑器 F5 与断点绑定仍需在自己的 VS Code/Delve 会话中观察。
