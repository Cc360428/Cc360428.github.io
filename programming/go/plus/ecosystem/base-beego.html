Beego 工程维护：模块、MVC 与排错 ​

本轮只做理论正文与源码静态复核；下列命令、示例和测试均未执行。已有输出按代码推演或历史记录理解，不作为本轮运行证据。

前置：Go HTTP 实践、Modules。Beego 适合按其路由、控制器和模块约定组织工程，先确认项目采用的主版本，再使用对应文档和 bee 工具。

模块与启动 ​

v2 的模块路径含 github.com/beego/beego/v2；旧示例里的 beego 包、ORM、bee 生成器与 v2 不一定同名或兼容。为新模块使用显式模块名 go mod init example.com/beego-app，选择依赖版本后再写入口：

go
package main

import "github.com/beego/beego/v2/server/web"

func main() { web.Run() }

这是框架入口，具体监听地址、端口和配置按工程控制，启动后通过实际端口请求确认行为。完整创建步骤和所选版本要求参见 Beego 官方仓库 与对应版本文档。

MVC 与代码生成 ​

controller 处理 HTTP 输入输出，model 表达数据与持久化，view 处理展示。生成代码只是起点，生成后检查参数校验、权限、错误、事务和字段暴露。bee appcode 的连接参数要来自本地开发配置，不把真实连接串写进文档或提交。先用 bee help 核对当前版本支持的子命令。

路由注解必须和实际方法、路径与响应一致；生成 Swagger 报错时，从具体注解定位，并在同版本工具链重新生成，不用不停重启数据库来处理文档错误。通用文档生成说明见 Swagger。

ORM 关系与标签 ​

旧 ORM 中 orm:"rel(fk)" 与 orm:"reverse(many)" 表达外键与反向一对多关系，方向应与业务模型一致。JSON 标签只控制 JSON 编解码，ORM 标签由 ORM 自己解释，不能互相替代。自动迁移、字段描述和数据库约束需检查所用 ORM 版本生成的 SQL，在测试库确认后再按发布流程执行。

故障定位 ​

现象先检查
数据库/Redis 连接被拒绝实际主机端口、服务监听和网络可达性，再检查认证与配置
QueryTable 找不到表模型注册、表名、schema 和当前连接库
端口不可达进程监听地址、容器映射、访问路径与环境网络规则
Swagger 生成失败注解语法、类型引用、生成器版本与工作目录
跨域请求失败浏览器预检、来源、方法、允许头和凭据要求

跨域必须按实际允许的来源配置；带凭据时不能把通配来源当作通用方案。数据库的启动/重启命令属于具体操作系统服务管理，不是 Beego 的通用修复步骤。

练习与验收 ​

用一个只读端点验证请求、路由与 JSON 响应，再加入无效参数测试；对数据库失败路径确认返回错误而非继续使用无效连接。旧工程升级主版本时，先列出包路径、生成器和配置差异，再分步运行测试。

最小端点的输入与预期 ​

上面的web.Run只是入口，不会自行创建业务JSON路由；它也没有给出完整MVC工程。只读端点练习可以沿用完整Go API的输入/状态码合同，再映射到旧工程现有控制器，不把其他框架包名混进Beego。理论案例：有效id返回200与约定字段；格式错误返回400；资源不存在返回404；依赖不可达返回受控5xx，不回传连接串。

题目：进程仍存活、端口可连，能否认为ORM查询正常？提示：区分进程、路由与依赖阶段。
