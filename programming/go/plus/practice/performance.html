Go 性能实验：基准、pprof、trace 与优化取舍 ​

前置：Benchmark、分配与 GC、执行追踪。目标是完成“问题 → 假设 → 正确性检查 → 测量 → 修改 → 重测”的闭环。使用 Go 1.27.2、纯标准库实验模块 examples/go/system-lab，不调用外部 API，不操作业务数据。

benchmark：先验证等价再比较 ​

两个函数都返回拥有独立存储的 []byte，内容为 task=<十进制整数>\n。它们不共享可复用全局缓冲区，调用者可以持有结果。Append 版本只为固定格式做专门化，不能推广成“fmt 总是应该替换”。

新目录保存下面的 go.mod、format.go、format_test.go 即可独立运行格式化实验；仓库用户直接进入完整模块，那里还有有界执行器，不必复制。所有文件完整列在本节和并发实践，没有省略号。

go.mod
text
module showdocs.example/system-lab

go 1.27.0
format.go（完整实现）
go
package systemlab

import (
	"fmt"
	"strconv"
)

func FormatLine(n int) []byte { return []byte(fmt.Sprintf("task=%d\n", n)) }

func AppendLine(n int) []byte {
	line := make([]byte, 0, 32)
	line = append(line, "task="...)
	line = strconv.AppendInt(line, int64(n), 10)
	return append(line, '\n')
}
format_test.go（完整单测与基准）
go
package systemlab

import "testing"

func TestLine(t *testing.T) {
	for _, n := range []int{-1, 0, 42, 2147483647} {
		if got, want := AppendLine(n), FormatLine(n); string(got) != string(want) {
			t.Fatalf("%q != %q", got, want)
		}
	}
	if string(AppendLine(42)) != "task=42\n" {
		t.Fatal("format")
	}
}

var lineSink []byte

func BenchmarkFormat(b *testing.B) {
	b.ReportAllocs()
	for b.Loop() {
		lineSink = FormatLine(42)
	}
}
func BenchmarkAppend(b *testing.B) {
	b.ReportAllocs()
	for b.Loop() {
		lineSink = AppendLine(42)
	}
}

模块目录执行，PowerShell/Bash 通用：

sh
go version
go test ./...
go test -run '^$' -bench 'Benchmark(Format|Append)$' -benchmem -count=5 .

预期单测通过，基准包含 BenchmarkFormat 和 BenchmarkAppend，每行有 ns/op、B/op、allocs/op。具体数字依赖 CPU、Go 版本、负载和运行状态，不写成固定正确性答案。b.Loop 是本课程工具链支持的基准循环，读取结果到包级 sink 保证结果被使用；不要在循环里输出日志或包含无关的启动/下载操作。单测覆盖负数、0、普通正数和较大整数，验证格式相同；如果扩充输入，先扩充语义测试。

基准只测试整数42和一次独立分配的短行；真实业务可能更长、输入分布不同或需要复用缓冲区。重复执行、保持相同 GOMAXPROCS 和系统负载，记录 Go/OS/CPU、命令、样本。确认分配与耗时差异方向稳定，再讨论是否值得增加专门逻辑。批处理吞吐与单次微基准不是同一个指标，不能据此承诺端到端加速比。

读一组真实结果 ​

在 Windows/amd64、Intel Core i7-14700、Go 1.27.2 上，以整数 42 运行三次 go test -run '^$' -bench 'Benchmark(Format|Append)$' -benchmem -benchtime=300ms -count=3 .。Fmt 的三次耗时落在 51.38–72.81 ns/op，每次 16 B、2 次分配；Append 为 23.12–23.95 ns/op，每次 32 B、1 次分配。此处 ns/op 是每次操作平均耗时，B/op 是每次操作累计分配的字节数。

对照 format.go，Append 版预留容量 32，再把整数写进去，避免中间格式化字符串。它做的分配次数少了一次，却为短行分配了更多字节。如果瓶颈是短命分配带来的 CPU 开销，值得继续在实际调用者中测；如果主要成本是长期缓存的小记录，还要测持有这些缓冲区的活堆。下一篇把同一改动放进一次返回 256 行的处理器，看代价如何累积。导出处理器诊断

profiles：CPU、分配、活堆和等待各回答什么 ​

运行下面命令会在当前实验目录覆盖 system-lab.test.exe 或 system-lab.test、cpu.out、mem.out。仅在实验目录使用这些固定文件名；分析结束后可按文件名删除，不操作生产数据。Go1.27.2、Bash 或 PowerShell7.4+：

sh
go test -run '^$' -bench BenchmarkFormat -benchtime=1s -cpuprofile=cpu.out -memprofile=mem.out .
go tool pprof -top cpu.out
go tool pprof -sample_index=alloc_space -top mem.out
go tool pprof -sample_index=inuse_space -top mem.out

以下命令还需要有界执行器和测试。在完整的 examples/go/system-lab 运行，或先从并发实践保存 worker.go、worker_test.go 和 cmd/lab/main.go，再采集等待和调度数据。

sh
go test -run TestRunBoundsAndJoins -count=1 -blockprofile=block.out -mutexprofile=mutex.out .
go tool pprof -top block.out
go tool pprof -top mutex.out
go run ./cmd/lab
go tool trace -d=parsed trace.out

预期每个 profile 均能由 pprof 解析，trace 有批次和区域；互斥样本可能为空，因为程序主要使用 channel、原子操作和极短临界区，这不是采集失败。CPU profile 对正在消耗 CPU 的位置采样，flat 是函数自身、cum 包括调用链；它通常看不到睡眠或大部分 I/O 等待。分配 profile 的 alloc_space 是累计分配样本，inuse_space 是采样时仍存活的样本；短基准中被覆盖的 sink 只保留最后一份，不能把累计分配当内存泄漏。

block profile 记录采样的同步阻塞，mutex profile 帮助定位锁竞争相关开销；它们有采样和归因规则，不是所有等待时间的完整清单。trace 展示调度与事件时序，适合回答哪个 G 在等谁，详见trace 阅读。先问“慢在哪里”，再选择工具，不能用一种图回答所有问题。

CPU 采集时间太短时没有足够样本，应延长 benchtime；内存采样会遗漏小分配，不等于没有分配。不要同时打开所有高开销分析再把受干扰的耗时当生产性能。需要行级查看时保持对应源码和二进制，再用 go tool pprof -list FormatLine cpu.out；若函数被内联，展示形式可能不同。图形化 Web 视图是可选项，文本 top/list 足以完成本次实验。

decision：用证据决定是否保留优化 ​

本项目正确性契约先固定为整数十进制、独立结果内存与换行，再比较 fmt 和 strconv.AppendInt。一个可复查的结论应写清：测的是哪种负载、哪些指标改变、是否增加内存保留或复杂度、哪些场景尚未测试。例如“42这一短行负载下，Append减少格式解析；测得分配/耗时见本机记录，未证明整个任务服务更快”。不能只写“性能提升很多”。

实际排查顺序：

  1. 固定业务正确性和可接受延迟/内存预算，建立代表性负载与基线。
  2. 区分 CPU 饱和、队列等待、下游等待、锁竞争、分配压力；检查错误率，避免用丢任务换吞吐。
  3. 用对应工具定位热点，再做一个最小改动，跑同样的单测、基准和负载。
  4. 比较多轮结果及资源预算；收益不稳定或复杂性过高时撤回。改并发数时同时检查下游容量、尾延迟和取消响应。

运行时调参不是代码性能问题的通用修复。若任务数增加导致内存上涨，先看背压与队列边界；若活堆稳定但分配很多，看分配与GC。多个维度互相约束，不能靠无限加 G、全局对象池或调大内存限制替代测量。

练习与自检 ​

把基准改为覆盖负数、小数值与较大整数的同一输入序列，两个实现使用相同数据；生成CPU和分配报告。写一段结论，包括一项收益、一项成本和一项未验证范围。解释为何 mem.out 的 alloc_space 很大而 inuse_space 很小仍可能正常。

参考解法

先添加等价单测，再在两个基准中用相同索引循环数据，输入构造放在计时循环外。保留结果使用，保持分配契约相同；不能让一个实现写共享缓冲区而另一个分配独立结果后声称公平比较。临时结果不断分配后被覆盖，累计分配增长而当前存活很少是正常现象；是否需要优化取决于GC/CPU和业务预算，不能单凭累计分配认定泄漏。提交命令和多轮原始结果，不填固定倍数。
