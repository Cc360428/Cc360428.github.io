Go 模块：依赖工作流与解析排障 ​

依赖、工具链与私有模块 ​

前置：工具链的首次运行、包与测试。包是一起编译的一组源文件，模块为一个或多个包提供发布路径和版本边界。同一仓库可以有多个模块，工作区只决定本次命令把哪些模块作为本地开发对象。

导入路径、依赖和校验 ​

go mod init example.com/team/app 创建模块。模块路径是其包导入路径的前缀。源文件 import 的是包；go.mod 的 require 记录对模块版本的最低要求。一个模块包含多个包，添加 require 不能解决源码中的循环导入。v2 及以上的常规模块会在模块路径中带上主版本，例如 Beego 的 github.com/beego/beego/v2；两个主版本可以是不同的模块标识。

go.sum 记录下载的模块内容或 go.mod 的校验和，同一个模块出现旧版本校验记录并不表示它们都参与当前构建。Go 1.21 起，go 指令规定最低工具链要求；toolchain 指令给出建议工具链。版本选择、内容校验和使用哪个编译器是三个独立问题。

为什么最终选这个版本 ​

假设应用同时依赖 A 与 B，两个分支依赖同一个模块路径 C。图中的版本都是依赖边上的最低要求。

最小版本选择（MVS）取依赖图对每个模块路径提出的最高最低版本。本例结果是 v1.5.0；即使仓库还发布过 v1.9.0，只要当前依赖图没有提出该要求，它也不会被自动选中。A 和 B 都以同一份选定的 C 参加构建，因此同一主版本维持兼容性很重要。若另一条依赖边要求 v1.6.0，结果才会随之提高。Go Modules：最小版本选择

用 go mod graph 看边上分别声明的要求，用 go list -m all 看本次选定版本，用 go mod why -m 模块路径 检查从主模块到某个依赖的包导入链。三者回答不同的问题。go get 模块@版本 修改当前模块的要求；只安装一个开发工具可使用 go install 工具包@版本。修改依赖后审阅 go.mod/go.sum 差异并运行行为测试。

replace、工作区和 vendor ​

replace 改写特定依赖内容的来源，可以指向本地目录。它单独存在时并不把未使用的模块加入构建。go.work 的 use 列出一起开发的主模块，作用于这次工作区构建，不会将多个包或发布版本合并。子模块在仓库外仍要有完整可解析的依赖。go mod vendor 将构建需要的依赖源码复制到 vendor，适合希望使用固定本地副本的发布流程。exclude 排除一个版本；retract 表示作者已撤回某些版本的使用建议。

代理和私有模块 ​

GOPRIVATE 是模块前缀的匹配规则，也为代理与公开校验库的跳过规则提供默认值。它不配置 Git 凭据。GOPROXY 用逗号连接时，一般只在 404/410 后尝试下一项；竖线连接允许在其他错误后继续。公开模块的校验和与内部仓库的认证是两层机制，排查时应保留原始错误和所处阶段。代理协议

本地双模块的检验目标 ​

先用 replace 运行消费方测试，再删除 replace 并启用 go.work，测试都应从相邻目录找到同一库。最后在移除 replace、退出工作区的条件下判断来源：如果这个教学模块没有发布，就不能假设其他机器也能下载到它。

两模块练习的完整文件 ​

新建同一个父目录下的 app、lib。以下共四个文件；两个模块都没有外部依赖。

lib/go.mod

text
module example.com/local/lib

go 1.27.0

lib/value.go

go
package lib

func Value() int { return 7 }

app/go.mod

text
module example.com/local/app

go 1.27.0
require example.com/local/lib v0.0.0
replace example.com/local/lib => ../lib

app/value_test.go

go
package app

import (
    "testing"
    "example.com/local/lib"
)

func TestLocalDependency(t *testing.T) {
    if got := lib.Value(); got != 7 {
        t.Fatalf("local library returned %d, want 7", got)
    }
}

从 app 目录运行 go test -count=1 -v .，应看到 TestLocalDependency 通过。再从 app 执行 go mod edit -dropreplace=example.com/local/lib，回到父目录执行 go work init ./app ./lib，进入 app 重跑同一测试。把库故意改为返回 8 得到断言失败，就能区分“发现了测试并调用到本地库”和“只成功编译”。工作区示例中的 v0.0.0 是本地教学占位版本，发布时须使用能实际解析的版本。

Go 模块依赖解析失败 ​

排查时按失败发生的位置取证。构建连 go.mod 都找不到、下载被代理拒绝，以及解析成功后业务测试失败，需要更改的对象不同。

从报错决定检查顺序 ​

确认当前模块与工作区 ​

先看 go env GOMOD GOWORK GOVERSION，记录工作目录与模块根。若编辑器成功而 CI 失败，比较二者是否使用了同一个 go.work 或仅在本机存在的 replace。整个模块缓存通常与这一层的错误无关。

审阅需要变动的文件 ​

go mod tidy -diff 显示根据导入关系应修改的 go.mod/go.sum；存在差异会非零退出，解析过程仍可能需要下载。明确变更后运行 go mod tidy、审阅差异。go mod verify 核对缓存内容的完整性，不能代替测试，也不证明业务兼容。

解释依赖和最终版本 ​

根据菱形依赖图，先找出提出较高要求的那条边，再核对选定版本。能够解释依赖为什么出现、哪个版本被选中，才适合决定升级或移除哪个上游模块。

常见报错 ​

no required module provides package ​

核对包的完整导入路径、主版本后缀、当前模块以及依赖来源。只有确认包确实属于该依赖，才去添加或修正 require。

401 / 403 / timeout ​

代理明示 401/403 时检查访问身份、组织权限、模块前缀与代理规则。超时则观察 DNS、代理可达性和时限。增大超时不能改变被拒绝的身份，不应把凭据填入模块路径或错误日志。
