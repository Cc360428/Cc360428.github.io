29.2 有界并发执行任务 ​

先读并发执行器与背压和请求取消。一个批次要说清三件事：最大同时执行数，第一项失败后的结果归属，函数返回时还有没有工作者。

初始化模板只共享一个结果。Go 1.21 起，sync.OnceValue 可把构造函数变成并发安全的取值函数。下面的变量定义在包作用域。所有调用者取到同一指针；共享对象后续若会被修改，仍须由对象自身同步。

go
type Client struct{}

var GetClient = sync.OnceValue(func() *Client { return &Client{} })

systemlab.Run 把输入下标交给工作者，结果写回原位置，后项先完成也能保持输入顺序。首错触发取消，等全部工作者退出后丢弃部分结果。忽略取消的回调可能一直阻塞。

go
// 在 examples/go/system-lab 模块的调用方中导入 showdocs.example/system-lab。
got, err := systemlab.Run(ctx, 2, []int{3, 1, 2}, func(_ context.Context, n int) (int, error) {
	return n * n, nil
})
// 成功时 got 为 [9 1 4]。

执行器的实现与测试里，TestRunBoundsAndJoins 收到两个回调已开始的通知后才放行，最后检查最大并发为 2、活动数为 0。TestRunCancellationAndError 分别覆盖父级取消和回调失败。发送任务下标和取消同时就绪时，派发仍可能成功。测试应检查并发上限、返回错误和退出时的活动数。

29.3 Worker Pool ​

输入发送者关闭任务通道，协调者等所有工作者退出后关闭结果通道。调用者持续消费到关闭。提前停止处理时先取消 context，再等结果通道关闭，否则工作者可能卡在发送结果这一步。

下面的函数接收非 nil 的 context、任务通道和回调，要求至少一个工作者。回调必须能够响应取消。消费者按各工作者实际发送的先后读到结果。两个回调几乎同时算完时，谁先发出去还受调度影响。需要首错传播或按输入顺序返回时，可用上节的执行器。

工作池实现（Go 1.25 及以上）
go
func StartWorkers(ctx context.Context, workers int, jobs <-chan int, work func(context.Context, int) int) (<-chan int, error) {
	if workers < 1 || jobs == nil || work == nil {
		return nil, errors.New("workers, jobs and work are required")
	}
	results := make(chan int)
	var wg sync.WaitGroup
	for range workers {
		wg.Go(func() {
			for {
				select {
				case <-ctx.Done():
					return
				case job, ok := <-jobs:
					if !ok {
						return
					}
					value := work(ctx, job)
					select {
					case results <- value:
					case <-ctx.Done():
						return
					}
				}
			}
		})
	}
	go func() {
		wg.Wait()
		close(results)
	}()
	return results, nil
}

把工作者数量改为 0，预期在启动任何 goroutine 前返回错误。令输入提前关闭，则已经取走的任务仍可正常发送结果，最后由协调者关闭通道。取消时允许已完成的结果与退出信号同时就绪。传给 WaitGroup.Go 的函数不能让 panic 逸出。

29.4 带 TTL 的简单缓存 ​

Get 先查键是否存在，再判断是否到期。截止时刻算过期，把当前时刻作为参数，就能在测试中精确控制边界。

go
type entry[V any] struct {
	value     V
	expiresAt time.Time
}

func liveValue[V any](item entry[V], now time.Time) (V, bool) {
	if !now.Before(item.expiresAt) {
		var zero V
		return zero, false
	}
	return item.value, true
}

共享 map 时，Set 在写锁内整体替换条目；Get 在读锁内取出条目和存在标志，再用上面的规则判定。复制条目只浅复制 V；若值为切片，调用者仍可改动同一底层数据，要明确谁拥有它。读时判断过期不会自动删除 map 中的对象。若决定惰性删除，在获取写锁后再次确认仍是过期版本，以免删除并发写入的新值。

零值可用的缓存
go
type Cache[K comparable, V any] struct {
	mu    sync.RWMutex
	items map[K]entry[V]
}

func (c *Cache[K, V]) Set(key K, value V, ttl time.Duration) {
	c.mu.Lock()
	defer c.mu.Unlock()
	if c.items == nil {
		c.items = make(map[K]entry[V])
	}
	c.items[key] = entry[V]{value: value, expiresAt: time.Now().Add(ttl)}
}

func (c *Cache[K, V]) Get(key K) (V, bool) {
	c.mu.RLock()
	defer c.mu.RUnlock()
	item, ok := c.items[key]
	if !ok {
		var zero V
		return zero, false
	}
	return liveValue(item, time.Now())
}

func (c *Cache[K, V]) Delete(key K) {
	c.mu.Lock()
	defer c.mu.Unlock()
	delete(c.items, key)
}

练习：在截止前一纳秒、截止时和截止后一纳秒分别取值，预期只有第一种命中。大量键长期无人读取时，还需要容量或清理策略；LRU 与 singleflight分别处理容量和同时回源。

29.5 生产者消费者安全关闭 ​

假定生产者发送两项，消费者处理第一项就失败。此时生产者可能仍在等待第二次发送；只有它知道何时可以关闭数据通道。这里由调用方同步消费，由它在所有返回路径取消子 context，并等待生产者的完成通知。函数返回时，两侧都已停止。

go
func Pipeline[T any](parent context.Context, items []T, handle func(context.Context, T) error) error {
	if handle == nil {
		return errors.New("handler required")
	}
	ctx, cancel := context.WithCancel(parent)
	out := make(chan T)
	done := make(chan struct{})
	go func() {
		defer close(done)
		defer close(out)
		for _, item := range items {
			select {
			case out <- item:
			case <-ctx.Done():
				return
			}
		}
	}()
	defer func() {
		cancel()
		<-done
	}()

	for item := range out {
		if err := ctx.Err(); err != nil {
			return err
		}
		if err := handle(ctx, item); err != nil {
			return err
		}
	}
	return ctx.Err()
}

成功时，发送者发完数据后依次关闭 out 和 done；消费者读完返回 nil。回调失败时，业务错误先成为返回值，延迟调用再取消并等待。父级已取消时返回取消错误。一个不理会 context 的阻塞回调仍能阻塞调用方；取消也不会撤销已写出的业务数据。

29.6 指数退避加抖动 ​

操作可安全重复、错误是暂时的且时间预算尚有剩余时才重试。次数包含首轮，最后一次失败直接返回。等待上限每轮翻倍，最大 30 秒，每轮在零与上限之间随机取值，让调用者错开重试。

带取消的重试循环
go
func Retry(ctx context.Context, attempts int, base time.Duration, retryable func(error) bool, call func(context.Context) error) error {
	if attempts < 1 || base <= 0 || base > 30*time.Second || retryable == nil || call == nil {
		return errors.New("invalid retry settings")
	}
	delay := base
	var last error
	for i := 0; i < attempts; i++ {
		if err := ctx.Err(); err != nil {
			return errors.Join(last, err)
		}
		last = call(ctx)
		if last == nil || !retryable(last) || i+1 == attempts {
			return last
		}
		timer := time.NewTimer(time.Duration(rand.Int64N(int64(delay) + 1)))
		select {
		case <-timer.C:
		case <-ctx.Done():
			timer.Stop()
			return errors.Join(last, ctx.Err())
		}
		delay = min(30*time.Second, delay*2)
	}
	return last
}

这里的 rand 来自 math/rand/v2，用途是普通抖动。初值最多 30 秒使翻倍在 time.Duration 范围内；零次尝试应直接报配置错误。父 context 的 deadline 约束总预算，call 必须把它传给下游。如果服务端可能已提交写入，先核对幂等与重试前提。

29.7 HTTP Client 安全请求模板 ​

调用方通过 context 的 deadline 或 Client.Timeout 设置总时限，两项都未设置时请求可以一直等待。收到非成功状态就返回 HTTP 错误，成功响应则限制读取大小，再解码 JSON。下面要求非 nil 的 Client、来源可信的 URL 和非负上限。为辨别“恰好够大”与“已经被截断”，读取上限加一个字节，所以先排除 math.MaxInt64。

有界读取与 JSON 解码
go
func FetchJSON[T any](ctx context.Context, client *http.Client, url string, maxBody int64) (T, error) {
	var zero T
	if client == nil || maxBody < 0 || maxBody == math.MaxInt64 {
		return zero, errors.New("nil client or invalid body limit")
	}
	req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
	if err != nil {
		return zero, err
	}
	resp, err := client.Do(req)
	if err != nil {
		return zero, err
	}
	defer resp.Body.Close()
	if resp.StatusCode < 200 || resp.StatusCode >= 300 {
		return zero, fmt.Errorf("unexpected HTTP status %d", resp.StatusCode)
	}
	data, err := io.ReadAll(io.LimitReader(resp.Body, maxBody+1))
	if err != nil {
		return zero, err
	}
	if int64(len(data)) > maxBody {
		return zero, errors.New("response body too large")
	}
	var value T
	if err := json.Unmarshal(data, &value); err != nil {
		return zero, err
	}
	return value, nil
}

若服务返回 503，调用者应看到状态错误，日志无需带出响应内容。若成功响应恰好等于上限且 JSON 完整，可以解码；多一个字节就返回大小错误，途中发生读取错误也要向上传递。提前关闭未读完的响应可能放弃一次 HTTP/1.x 连接复用，这里优先限制资源占用。来源由用户提供的 URL 还需应用的出站访问策略。

29.8 优雅关闭模板 ​

服务收到终止通知后先停止接新流量，再用独立的短期 context 等待在途请求。若直接把已取消的信号 context 传给 Shutdown，它会失去等待预算。下面的函数在总预算用尽后强制关闭仍打开的普通连接，并将超时保留在返回的错误链中。

go
func drainHTTP(srv *http.Server, budget time.Duration) error {
	ctx, cancel := context.WithTimeout(context.Background(), budget)
	defer cancel()
	if err := srv.Shutdown(ctx); err != nil {
		return errors.Join(err, srv.Close())
	}
	return nil
}

外层要同时观察服务启动错误和停机信号；主 goroutine 必须等待 drainHTTP 完成再退出。WebSocket 等接管的连接以及后台 worker 应由各自的所有者通知并等待。测试可让一个请求停在可释放的屏障上，然后分别检查“在预算内完成”和“超时强制关闭”两条路径。HTTP Server.Shutdown
