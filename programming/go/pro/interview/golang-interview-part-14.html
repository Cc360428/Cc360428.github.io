27. 高频代码陷阱 ​

先回顾闭包、方法与接口和共享状态。遮住每题的解释，先回答三件事：代码能否编译，结果由哪条规则保证，换一种输入或调度顺序会发生什么。

27.1 range 循环变量地址问题 ​

循环内取得的地址，是原切片元素、每轮变量，还是同一个外部变量？改用 = 会怎样？

核对原因

Go 1.22 及以上语言版本中，for _, item := range items 每轮声明新的迭代变量。改成向循环外声明的 item 用 = 赋值，各轮仍共用同一变量。两种情形下，切片迭代值本身都是元素副本。阅读旧项目时检查模块的语言版本。

  • 模块 Go 版本和实际工具链。
  • 外层预声明并被重复赋值的变量。
  • map value 本身为临时副本。
  • 闭包是否共享了其他可变状态。

兼容且清晰的写法：

go
for _, item := range items {
	item := item
	go func() {
		process(item)
	}()
}

如果需要原切片元素地址：

go
for i := range items {
	use(&items[i])
}

27.2 defer 与 nil 方法接收者 ​

client.Do 失败时，先登记 defer resp.Body.Close() 再检查错误会发生什么？

核对原因

defer 注册时函数值和参数立即求值。像 defer resp.Body.Close() 必须在确认 err == nil 且 resp、Body 有效后执行。

27.3 shadowing 变量遮蔽 ​

预测：cond 为真且 load 返回错误时，下面的函数片段最终返回哪个错误？

go
var err error
if cond {
	value, err := load()
	_ = value
	_ = err
}
return err
核对作用域

:= 所在的 if 块定义了新的 value 和 err。return err 读取外层变量，其值仍为 nil。若业务要求传播失败，就在 if 块中检查并返回 load 的错误；若后续确实要用同一个变量，先声明需要的变量，再用 = 赋值。

27.4 nil receiver 可以调用方法吗？ ​

指针接收者为 nil 时，方法能否进入？哪一步才需要有效对象？

核对原因

可以，只要方法内部能安全处理 nil：

go
func (n *Node) Len() int {
	if n == nil {
		return 0
	}
	return 1 + n.Next.Len()
}

调用方法本身不一定 panic，真正解引用 nil 字段才会 panic。

27.5 把 Mutex 复制了 ​

预测：var c Counter 后调用一次 c.Inc()，原来的计数发生了什么？

go
type Counter struct {
	mu sync.Mutex
	n  int
}

func (c Counter) Inc() {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.n++
}
核对所有权

值接收者复制了 mu 和 n，调用结束后原对象仍为零。把签名改为 func (c *Counter) Inc()，所有调用才会在同一把锁内修改同一个计数。已经使用过的互斥锁禁止复制，go vet 的 copylocks 检查能指出部分这样的代码。

27.6 发送到已关闭 channel ​

两个发送者各自执行了最后一次发送，谁有足够信息关闭共享通道？

核对原因

仅用 recover 掩盖 send on closed channel 不是正确并发设计。应明确 channel 所有权，让关闭和发送流程由同一协调机制控制。

27.7 goroutine 中修改外层 error ​

循环变量已经按轮独立，多个 goroutine 仍把错误写入同一个外层变量，会怎样？

核对原因
go
var err error
for _, job := range jobs {
	go func() {
		err = process(job) // 数据竞争
	}()
}

应使用错误 channel、带取消的任务组，或每个 goroutine 返回独立结果。

27.8 time.Ticker 忘记停止 ​

只调用 ticker.Stop() 后，等待 ticker.C 的 goroutine 会自动结束吗？

核对原因
go
ticker := time.NewTicker(time.Second)
defer ticker.Stop()

Stop 会阻止后续 tick，但不会关闭 ticker.C。单纯 for range ticker.C 的工作者仍可能等待；用 select 同时监听 ctx.Done()，让所有者可以等待它返回。Go 1.23 起，启用新计时器语义的程序还允许 GC 回收不可达的 ticker。只要工作者仍在等通道，它的退出仍须有自己的信号。Go 1.23 计时器语义

27.9 map 返回内部可变对象 ​

持锁读出 map 中的切片后释放锁，调用者改元素时，原来的锁还能保护修改吗？

核对原因

即使 map 读操作加了锁，返回内部 slice/map/指针后调用方仍能在锁外修改共享对象。

解决：

  • 返回副本。
  • 返回不可变快照。
  • 提供受控方法而不是暴露内部对象。

27.10 错误使用 time.After 做循环超时 ​

在高频循环中反复使用 time.After，分配成本与不可达计时器的回收是同一件事吗？

核对原因

高频循环每次创建新 timer 会增加对象和运行时 timer 压力。复用 time.Timer，或重新设计成统一 ticker/context deadline。

27.11 忽略 HTTP 状态码 ​

收到 404 时，client.Do 的 error 一定非 nil 吗？

核对原因
go
resp, err := client.Do(req)

err == nil 只表示 HTTP 往返成功，不表示业务成功。404、500 都可能是 nil error，必须判断状态码并限制读取错误响应体。

27.12 JSON 把 int64 交给 JavaScript ​

相邻的两个 int64 ID 经前端的 Number 转换后，可能显示为同一个数吗？

核对原因

JavaScript Number 不能精确表达所有 int64。用户 ID、订单 ID、雪花 ID 应与前端约定为字符串，或使用明确支持大整数的方案。

27.13 锁内调用外部函数 ​

持锁调用一个可能回调当前对象的函数，延迟或重入会怎样影响其他请求？

核对原因

回调、RPC、数据库访问可能慢、重入或 panic，持锁执行会扩大临界区甚至死锁。通常先在锁内复制必要状态，解锁后执行外部操作。

27.14 无界 goroutine ​

任务到达速度持续超过完成速度时，每个请求新建一个 goroutine 会把等待转移到哪里？

核对原因
go
for req := range requests {
	go handle(req)
}

流量突增时可能导致 goroutine、内存和下游请求无限增长。使用 worker pool、semaphore 或有界队列。

27.15 错误的 semaphore 退出 ​

等待并发令牌时父级取消，应怎样退出？已经取得的令牌由谁归还？

核对原因

获取 semaphore 后必须确保释放，即使函数返回或 panic：

go
select {
case sem <- struct{}{}:
case <-ctx.Done():
	return ctx.Err()
}
go func() {
	defer func() { <-sem }()
	process()
}()

取得令牌后由启动的 goroutine 归还。令牌与取消同时就绪时两条分支都有机会执行；涉及副作用的任务还需处理自己的取消与幂等语义。
