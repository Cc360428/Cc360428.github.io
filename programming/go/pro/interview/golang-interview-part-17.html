29.9 LRU Cache 核心设计 ​

先比较上一节的TTL 缓存：过期时间回答“值是否还能使用”，LRU 回答“容量满时先移除谁”。一个仍在有效期内的键也可能因容量不足被淘汰。

  • map 把键关联到链表节点，平均 O(1) 查找。
  • 双向链表在已有节点指针时可以 O(1) 移动到头部或删除尾部。
  • map 与链表必须始终一一对应。命中也会改变链表顺序，并发 Get 不能只持读锁后直接移动节点。

操作：

  • Get：map 找节点，移动到头部。
  • Put：存在则更新并移动；不存在则插入头部。
  • 超容量：删除尾节点和 map key。

容量为 2，依次写 A、写 B、读 A、写 C，应淘汰 B；查找 B 要返回未命中，链表中的两个键也必须与 map 一致。若允许容量为零，要定义为不保留任何项，或在构造时拒绝。仅用 map 无法记录访问顺序。

29.10 singleflight 思路 ​

同一进程内多个请求同时缺失同一键时，可以合并正在进行的加载。完成后的下一次调用仍可重新加载；如果希望跨时间复用结果，还要把成功值存入缓存。

核心状态：

text
map[key]*call
call:
  done channel
  result
  error

流程：

  1. 加锁检查 key 是否已有 call。
  2. 有则取得这个 call 的引用，释放锁后等待 done。
  3. 无则创建 call，解锁后执行加载。
  4. 加锁后发布结果并删除此 call，关闭 done 通知所有等待者，再解锁；等待者从已完成的 call 取得同一个结果或错误。

调用者 A 超时不必然表示 B 也放弃了等待。使用 singleflight.Group.DoChan 时，每个调用者可分别监听自己的 context；共享加载是否结束由它的所有者决定。合并键要包含会改变结果的身份范围和参数。两个不同用户若不该得到相同数据，就不应共享这个键。singleflight

30. 面试回答方法与复习路线 ​

30.1 一个技术题应该怎么回答？ ​

推荐五层结构：

  1. 一句话结论：先回答是什么。
  2. 核心原理：解释内部机制。
  3. 使用场景：什么时候用。
  4. 风险与取舍：什么时候不能用。
  5. 项目实践：结合真实问题、指标和结果。

例如“channel 和 mutex 怎么选”：

channel 更适合任务传递、所有权转移和流水线；mutex 更适合保护共享状态和短临界区。 channel 通过发送接收建立同步，mutex 通过临界区保证互斥。 我会先根据数据所有权选模型，再通过 race detector 和 benchmark 验证。 如果只是高频访问一个 map，用 channel 把每次读写都串行化可能增加复杂度；如果是 worker pool 和停止通知，channel 更自然。

30.2 项目题如何使用 STAR 表达？ ​

  • Situation：当时业务背景和问题。
  • Task：你的职责和目标。
  • Action：你做了什么，为什么这么做。
  • Result：量化结果、风险变化和后续复盘。

以有界执行器的实验为例，可以把任务说成“同时处理多个输入，并保证返回时没有活动回调”。实验用可释放的屏障让两个回调的生命周期重叠，原子计数记录最大并发与退出后的活动数。断言支持“最多有两个活动回调，且返回时均已退出”。要解释 CPU 是否实际并行或线上 P99 是否改善，还需要执行追踪或服务采样。

要写自己的性能案例，附上输入规模、采样窗口、基线和改动后相同负载的复测值。若只做了本地实验，就报告本地指标；有线上采样时，再说明观察到的错误率或延迟分位数以及仍无法排除的因素。基准与复测

30.3 七天快速复习计划 ​

第 1 天：基础与容器 ​

  • 类型、零值、值传递。
  • string、rune、UTF-8。
  • slice 共享、扩容、内存滞留。
  • map 原理与并发限制。
  • interface nil。

第 2 天：函数与工程语义 ​

  • defer、panic、recover。
  • error wrap、Is、As。
  • 方法集、指针接收者。
  • 泛型。
  • 包初始化和 modules。

第 3 天：并发 ​

  • GMP。
  • channel、select。
  • context。
  • Mutex、RWMutex、WaitGroup、Once、Pool。
  • 数据竞争、死锁、goroutine 泄漏。

第 4 天：内存和 GC ​

  • 逃逸。
  • 分配器。
  • 三色标记。
  • 写屏障。
  • GOGC、内存限制。
  • pprof 和 trace。

第 5 天：网络和存储 ​

  • TCP 字节流、粘包拆包。
  • HTTP Client/Server 超时和连接池。
  • database/sql。
  • 事务、索引、慢查询。
  • Redis 缓存问题和锁。

第 6 天：微服务稳定性 ​

  • gRPC、Proto 演进。
  • Kratos 分层。
  • 超时、重试、限流、熔断。
  • 幂等、消息、Outbox。
  • 优雅启停和可观测性。

第 7 天：模拟面试 ​

  • 60 道快问快答。
  • 手写 worker pool、LRU、并发安全缓存。
  • 准备 3 个 STAR 项目案例。
  • 复盘不会的问题并回到原理。

30.4 一个月深入路线 ​

第 1 周：语言与标准库 ​

  • 每天阅读一个标准库小接口：io、context、errors、sync。
  • 写 slice/map/interface 小实验。
  • 使用 -gcflags="-m=2" 观察逃逸。

第 2 周：并发与运行时 ​

  • 实现 worker pool、pipeline、超时与取消。
  • 故意制造 race、deadlock、goroutine leak，再用工具定位。
  • 阅读 runtime 调度和内存相关文章，并结合 trace 实验。

第 3 周：服务与数据 ​

  • 写一个带 MySQL、Redis、HTTP/gRPC 的小服务。
  • 配置连接池、超时、限流和 graceful shutdown。
  • 加 metrics、logs、traces。

第 4 周：性能与项目表达 ​

  • 建立压测基线。
  • 采集 CPU/heap/mutex/goroutine profile。
  • 完成一次基于证据的优化。
  • 总结 3 个项目案例和 10 个故障排查案例。

跨专题复习边界 ​

Go 服务面试还会讨论语言之外的机制，按实际岗位另行复盘：

  • 网络专题：TCP 的 TIME_WAIT 与 2MSL、连接建立关闭、PING 与跨网段通信；gRPC 调用边界见第 24 章。
  • MySQL 与 Redis：索引、隔离、日志、缓存一致性及锁；第 19、20 章侧重 Go 调用方的使用与故障。
  • Docker 与 Kubernetes：镜像、命名空间、组件、工作负载、Pod 网络与持久化；它们不属于 Go 语法前置。
  • 算法与设计模式需要单独练习。用 Go 算法与容器实践验证不变量；单例示例见第 29 章，项目中优先明确构造与依赖。

附录 B：按设计路径回看 ​

完成一次口述或手写后，沿同一条数据和生命周期路径核对，避免把零散结论当成完整设计。

核对路径具体内容
语言语义参数复制与共享数据 → append 返回值 → 接口 nil
并发协议任务所有者与退出 → 通道关闭职责 → 等待阶段
内存证据逃逸 → GC 调节 → 存活与累计分配
服务调用连接复用 → 响应体 → 事务提交
稳定性与优化锁的故障边界 → 重试预算 → 测量与复测
