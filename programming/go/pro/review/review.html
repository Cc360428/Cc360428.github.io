Go 基础复习：用实验回答切片、接口、取消与事务问题 ​

适合已经走完基础路线、需要巩固或面试前自测的读者。本文不复制整套示例：先遮住答案回答，再到链接中的完整程序运行验证。示例环境沿用 Go 1.27.2，Windows/Linux 的验证属于历史记录，本轮只复核答案与对应源码，未执行示例；macOS 仅作平台说明，本项目不执行平台运行验证。此页覆盖首批能力，不代表完整高级面试课程。

切片复制是否独立 ​

题目：把一个切片赋给另一个变量后，修改第二个切片的元素，第一个是否受影响？append 后又如何？不要只答“引用类型”，要解释容量和底层数组。用切片的完整实验预测每行输出，再运行核对。

参考解法

赋值复制切片描述信息，两个切片可能共享底层数组；修改共享元素会相互影响。append 是否分配新数组取决于容量，不能凭变量名判断是否独立。需要独立可修改的元素存储时新建切片并 copy；若元素本身含指针，copy 仍不是任意对象图的深拷贝。预期应能解释示例中共享修改和独立副本的区别。

为什么 interface nil 判断失败 ​

题目：一个具体指针为 nil，把它赋给接口后，接口是否等于 nil？返回 error 时应如何避免这个问题？先完成接口 nil 实验。

参考解法

接口包含动态类型和动态值。有具体指针类型但值为 nil 的接口，整体仍不为 nil。表示成功时返回字面 nil，而不是携带 nil 指针的 error 接口。预期能说明“具体指针 nil”和“接口 nil”为什么不同；不能靠打印外观判断。

context 取消会结束 goroutine 吗 ​

题目：消费者提前退出，生产者阻塞在发送上；只调用 cancel 是否足够？给出退出路径，再核对取消与完成通知。

参考解法

取消是通知，不会强制杀死 goroutine。阻塞发送处需要通过 select 同时监听 ctx.Done；收到取消后返回，调用者等待完成通知，才能证明工作已经结束。预期程序不会依赖 sleep 猜测退出时间。共享状态另需同步，context 本身不消除数据竞争。

事务失败时哪些数据应该回滚 ​

题目：更新任务状态与写入状态变更记录属于一个业务操作，插入 changes 失败时，能否留下更新后的任务状态？在项目事务测试中找出失败注入和持久化断言。records 保存学习心得，是独立操作，不属于这里的状态变更事务。

参考解法

更新 tasks 与插入 changes 应在同一事务内完成，两步都成功才提交。预期 changes 插入失败后任务状态回滚，状态变更记录数也不增加。事务外执行其中一步、忽略 Commit 错误或只检查 HTTP 状态，都不能证明数据库状态正确。核对项目中的 TestStatusRollback，而不是学习心得 records 的创建测试。

用项目证据组织面试回答 ​

选一个问题，按“结论 → 适用条件 → 最小实验 → 失败情形 → 项目中的验证”回答。自测标准是能预测输出、能解释错误结果、能指出验证位置；只记住术语不算通过。答错时回到同一正文，不另抄一份答案笔记。
