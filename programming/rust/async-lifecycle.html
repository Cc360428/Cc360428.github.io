Rust 异步任务：所有权、取消与排障 ​

Send、static 与取消 ​

前置：Future/poll。普通 await 发生在当前任务内部；spawn 则创建独立调度的任务。决定 spawn 之前先问：谁拥有数据、谁观察失败、谁负责退出。示例未执行。

Send 与 static ​

Rust任务Send与static约束针对跨 await 保存的状态和独立任务的生命周期：tokio::spawn 要求 Future 与结果是 Send + 'static。Send 允许任务被线程池转移，'static 要求任务不借用可能提前消失的栈数据，并不表示任务一定活到进程结束。

async move 把捕获值移动进 Future；若捕获的是 &String，移动的仍是引用，并未变成拥有 String。应把拥有的数据 move 进去，或按需要克隆 Arc；Arc 只保证引用计数线程安全，不会把内部 Rc/RefCell 自动改成 Send/Sync。Rc 若必须跨 await 保存会使 Future 非 Send；若它在 await 前的独立词法作用域内就销毁，则应按实际状态判断，而非看到 Rc 就一概判定失败。接口依据 Tokio spawning。

LocalSet 与非 Send ​

Rust LocalSet与非Send任务适用于 Rc 等不能跨线程转移的状态：LocalSet 将本地任务限制在同一线程，spawn_local 不要求 Send，但独立任务仍需 'static。它不是把借用改成任意长寿命的豁免，也不等同于普通 current_thread runtime。

stable 的典型结构是同步入口创建 current_thread Runtime，再 block_on(local.run_until(async { ... }))；在其中调用 spawn_local，并 await 得到的句柄。也可在合适的顶层 main/test 入口 run_until，不能随意从 tokio::spawn 内嵌套驱动它。LocalSet 内调用 tokio::spawn 创建的仍是普通 Send 任务，不会自动留下来。若本地状态是业务要求，选择 LocalSet；若只是可移植的输入 Vec，直接拥有它更简单。参见 Tokio LocalSet。

spawn 之后谁负责 ​

Rust spawn任务所有权需要同时记录数据所有者与回收者：Future 拥有输入，JoinHandle 持有观察输出的入口；丢弃 JoinHandle 会分离任务，不是取消。因此“函数返回时局部句柄已经 drop”不能证明任务停止。本工程把句柄责任交给 JoinSet，成功和失败都走回收路径。

若任务返回 Result<T,E>，await JoinHandle 得到 Result<Result<T,E>, JoinError>：内层是业务失败，外层是 panic 或取消；把两层混成一个 unwrap 会隐藏错误来源。默认 unwind 下任务 panic 可以通过 JoinError 观察，但 panic hook 仍可能输出文本；panic=abort 则终止进程，不在本例的可恢复保证内。拥有数据并不意味着不需关闭外部资源，数据库提交等副作用要另定协议。

abort 与合作取消 ​

Rust abort与合作取消的区别是销毁 Future 和业务退出协议：abort 发出取消请求，任务在调度机会停止并运行已初始化局部变量的析构；它不会抢占当前同步计算，也不会替你异步回滚。等待句柄或 drain JoinSet 才能观察取消已完成。合作取消则通过标志、通道或 CancellationToken 在业务安全边界退出。

本工程计算有界片段后 yield，失败时停止补充并 abort_all、join 到空，保证 analyze 被完整 await 返回后没有遗留计算。外部直接 drop analyze 时，其 JoinSet Drop 请求取消，但析构本身不能 await；不能把这个外部取消情形写成“已经等所有析构完成”。需要可等待的显式关闭协议时，应让上层持有控制通道和 JoinHandle 并发出关闭后继续 await，而非任意丢掉父 Future。

select 与取消安全 ​

Rust取消安全与select分支关乎丢弃未完成 Future 后能否无损重试：select 竞争的另一分支完成时，未选中的分支 Future 会被丢弃；已经写出的字节或移出的消息不会自动复原。取消安全不等于没有副作用，而是必须按具体操作契约判断重建该 Future 是否丢进度。

JoinSet::join_next 在 select 中被取消时保证不移除任务，因而可继续回收。相反，read_exact/write_all 可能已推进部分字节，不能盲目从头重复；先保存进度或采用有明确取消语义的分段协议。select 在同一任务内并发轮询分支，不会自动并行；一个阻塞分支仍会拖住其他分支。本例未用 select 模拟超时，避免把“超时到达”误写成“阻塞已结束”。参见 select 取消安全表。

练习 ​

① 把 String 改成 &String 后再 async move，为什么仍可能不满足 static？② 在 LocalSet 中把 spawn_local 改成 tokio::spawn，Rc 能否继续跨 await？③ 为什么错误后还要 join，不能只 abort_all？④ 超时分支胜出后可以无条件重做整次 write_all 吗？

参考解法 ​

① move 转移引用本身，引用指向的栈值仍可能提前销毁。② 不能，普通 spawn 保留 Send 要求。③ 请求取消与完成析构是不同阶段；继续 join 才能观察退出。④ 不行，之前可能已写出部分字节，重放需考虑重复提交或维护进度。

锁、阻塞、取消与清理证据 ​

前置：完整工程。这里给出诊断顺序和可复核证据，不宣称已经执行 Rust。先区分编译错误、业务 Err、JoinError、运行时配置错误与活性问题，再选择定位动作。

future cannot be sent ​

Rust future不能Send诊断先看跨 await 状态与捕获来源：错误指向 Rc、RefCell 的借用或非 Send guard 时，沿编译器标注找到该值跨越的 await；不要用 unsafe impl Send 消除症状。优先让短命局部值在明确词法块内销毁，或把拥有数据 move 进去；必须线程本地的状态改用 LocalSet。

若报 borrowed value does not live long enough，检查 async move 捕获的究竟是 String 还是 &String，任务能否越过调用栈返回。单线程 Runtime 也不改变普通 spawn 的 Send + 'static 合约。改变数据结构之前先判断是否根本不需要 spawn：当前任务内的直接 await 可以保留受约束的局部借用。

锁跨 await ​

Rust锁跨await诊断需要区分锁类型与等待图：std::sync::Mutex 的锁获取会阻塞线程，guard 通常也妨碍 Send；短临界区且不跨 await 的普通数据保护可以使用它。先在词法块内提取拥有的快照，再释放 guard，之后才 await，通常比一律换异步锁简单。

Tokio Mutex 的 lock().await 等待时让出任务，guard 设计上可跨 await，但不代表这样必然正确。若任务A持锁等待任务B，而B需要同一把锁，就算编译通过也会死锁；长期 I/O 放在锁内还会串行化所有访问。对独占 I/O 资源可让一个任务拥有它、其他任务通过有界通道发请求，明确队列容量与关闭规则。参见 Tokio Mutex 的适用范围。

阻塞与 spawn_blocking ​

Rust阻塞边界与spawn_blocking诊断关注一次 poll 能否及时返回：同步文件读取、长CPU循环、阻塞锁都可能占住工作线程。async move 只是构造 Future，不会把内部同步函数变为非阻塞。本工程把一次性文件读取放在运行时外，数值任务分片并 yield；不将其包装成高吞吐CPU方案。

spawn_blocking 把同步闭包提交到阻塞线程池，适合确实必须调用的同步 API，但已经开始执行的闭包不能靠 abort 取消；排队未开始的可能阻止启动，不可当成可靠抢占协议。超时只意味着调用方停止等待，底层工作可能继续。大量 CPU 任务要另设容量上限，长驻工作宜专用线程或进程；Runtime 关闭也不能替你终止无限阻塞闭包。参见 spawn_blocking 1.48.0。

回收与错误定位 ​

Rust任务回收错误定位分为业务失败与JoinError：ERR 是业务拒绝，sum overflow 是计算错误，panic 则由 JoinError 表示；is_cancelled 与 is_panic 可进一步区分。panic=abort 不遵守任务级恢复假设，必须在部署配置中单独确认。

排查“返回后仍有工作”时先看是否 drop JoinHandle 分离了任务，是否只 abort 未 join，是否上层直接取消了 analyze。完整工程正常 await 返回后 active 应为0；未运行测试时这只是断言设计，不能称已观察事实。多个任务同时失败时返回首个被观察到的错误，不承诺固定错误顺序；失败路径还需确保不再补充新任务。

配置与验证边界 ​

Rust异步配置验证边界包括编译特性与资源驱动：找不到测试宏先查 macros，找不到多线程 Builder 查 rt-multi-thread；时间或网络资源不可用再查相应 feature 和 enable_time/enable_io。不要为当前无I/O实验无差别启用 full，也不要把缓存依赖缺失和类型错误混为一谈。

本批仅解析 TOML、JSON、Markdown include 路径并人工核查源码，示例未执行。下一阶段读者应运行测试与失败输入，检验实际工具链、平台和 panic 配置；并发测试避免靠 sleep 排队猜测，使用 oneshot 确认进入、join 确认退出，测试容量上限而非调度顺序。站点构建通过只能证明内容可发布，不能证明 Tokio 工程编译或测试通过。

练习 ​

① 给同步无限循环外层加 tokio::time::timeout 能保证退出吗？② 把 std Mutex 换成 Tokio Mutex，A持锁等B、B等锁的流程会自动修复吗？③ abort_all 后立即打印 active，为何不能要求一定为0？

参考解法 ​

① 不能，当前线程可能根本无法推进定时器和超时分支；已启动阻塞工作也不可因此停止。② 不会，等待图的环仍在。③ 请求与执行取消有时间差，应 drain 后再检查；若是外部取消父 Future，要有额外可等待的关闭协议。
