JVM 线程诊断：用锁拥有者解释阻塞 ​

一次请求迟迟不返回时，先写下你要验证的假设。例如“工作线程在等待另一个线程释放同一个监视器”。这个假设可以同时预测线程状态、锁对象和拥有者。只有一张 CPU 图时，三项都还未知。

解读线程状态之前先定位等待点 ​

进入别人持有的 synchronized 监视器会表现为 BLOCKED。已取得监视器的线程调用 Object.wait 会释放它并等待通知；阻塞队列、CountDownLatch 等也可能通过 park 等待，表现为 WAITING 或 TIMED_WAITING。等待外部 I/O 时可能显示 RUNNABLE，状态名不能独立证明 CPU 正在忙。诊断要同时读栈顶、持有的锁、等待的锁及线程名称。

下面的探针让 main 先持锁，启动一个命名线程。启动信号只表明它走到了入口，随后通过管理 API 取得锁拥有者，最后验证释放锁后工作确实完成。保存为 Contention.java，执行 java Contention.java。

java
import java.lang.management.ManagementFactory;
import java.lang.management.ThreadInfo;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicBoolean;

class Contention {
    public static void main(String[] args) throws InterruptedException {
        var gate = new Object();
        var started = new CountDownLatch(1);
        var finished = new AtomicBoolean();
        var worker = new Thread(() -> {
            started.countDown();
            synchronized (gate) { finished.set(true); }
        }, "reader");

        var threads = ManagementFactory.getThreadMXBean();
        synchronized (gate) {
            worker.start();
            if (!started.await(5, TimeUnit.SECONDS)) throw new AssertionError("start");
            long deadline = System.nanoTime() + TimeUnit.SECONDS.toNanos(5);
            ThreadInfo info;
            do {
                info = threads.getThreadInfo(worker.threadId());
                if (info != null && info.getThreadState() == Thread.State.BLOCKED) break;
                if (System.nanoTime() - deadline >= 0) throw new AssertionError("sample");
                Thread.sleep(1);
            } while (true);
            System.out.println(info.getThreadName() + " waits for " + info.getLockOwnerName());
        }
        worker.join(5000);
        if (worker.isAlive() || !finished.get()) throw new AssertionError("completion");
    }
}

从一张快照到可重复的结论 ​

从终端启动时预期为 reader waits for main。主线程释放监视器后，worker 获得锁、写入完成标志并终止。示例使用平台线程，ThreadMXBean 对平台线程的结果不能直接推广到虚拟线程。采样上限只保证实验能退出，并不规定 JVM 必须在多少毫秒内调度线程。

在长时间运行的同权限进程上，可用 jcmd -l 确认进程，再对目标执行 jcmd <pid> Thread.print -l。多次采样若都显示同一拥有者，下一步是检查它在临界区内做什么；若不同线程轮流持锁且完成数持续增加，更可能是争用。要判定死锁，须找到互相等待、无法解除的依赖环。要解释 GC 或 CPU 热点，则应另取 GC 事件或带时间范围的采样记录。

复盘时列出三条可验证的观察：谁等谁、持锁者何时释放、工作是否退出。若把 join 移进 main 的同步块，工作线程无法在 main 仍持锁时完成，带期限的等待会到期；这只构成有限时间的相互等待。若改用无期限等待才会让二者永久互卡。JDK 21 ThreadMXBean · jcmd 说明
