从 .csproj 到可执行程序：构建、引用与测试入口 ​

同一目录里有 Report.cs、业务入口、测试入口和实验入口。编译器面对的是某个项目选出的源文件和引用，而非目录里肉眼可见的所有文件。SDK 风格项目默认纳入目录树中的 C# 文件；这个仓库把几个项目放在同一目录，特意关闭默认编译项，并为每个项目列出自己的文件。

沿项目文件寻找入口 ​

examples/csharp/ledger/Ledger.csproj 以 OutputType=Exe、TargetFramework=net10.0 编译 Program.cs 和 Report.cs。Tests.csproj 只编译 Tests.cs，再通过 ProjectReference 引用业务项目，可直接调用公开类型。Lab.csproj 只编译性能实验。引用使构建系统先准备所需程序集，不会把另一个项目的源文件再当成本项目的入口。

同目录的 Directory.Build.props 按项目名分别设置 obj 和 bin，防止中间文件、依赖清单和最终产物互相覆盖。Nullable 控制编译器空状态分析；TreatWarningsAsErrors 会让受约束的警告导致构建失败。这些选择属于项目的编译约定，程序运行时依旧要检查外部输入。

分开观察构建和运行 ​

在示例目录执行以下命令。SDK 列表用于确认具备 net10.0 构建能力；只安装运行时的机器也许能执行一个已有 DLL，却无法完成该项目的编译。

shell
dotnet --list-sdks
dotnet build Tests.csproj
dotnet run --no-build --project Tests.csproj
dotnet bin/Ledger/Debug/net10.0/Ledger.dll

第二条应连同业务引用一起构建，第三条执行仓库的自测程序，检查解析、累计、借用及取消。最后一条故意缺少输入文件参数，业务应写用法到 stderr 并返回 2；PowerShell 中此时查看 $LASTEXITCODE。若读者刚在 Release 构建，则应换到对应的 Release 目录。--no-build 适合重用刚刚生成的同一配置，修改源文件后需重新编译。

为什么两个绿色退出码可能含义不同 ​

Tests.csproj 的检查写在控制台 Main 内，由 dotnet run --project Tests.csproj 触发。使用 dotnet test 的测试项目通常需要已配置的测试运行器和可发现的测试；仅看到构建成功不能证明这里的 Main 已被执行。验收时应同时记录目标项目、运行命令、断言输出和退出状态。若要定位编译错误，先分辨是“选择了错误项目”“目标框架无法解析”还是“源代码类型检查失败”，三者的改动位置不同。.NET 项目 SDK · dotnet run
