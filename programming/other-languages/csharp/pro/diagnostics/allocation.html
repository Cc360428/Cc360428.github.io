.NET 分配诊断：同一线程的分配量与存活对象 ​

一段计算完成后堆大小变化很小，期间仍可能反复分配许多短命对象。GC.GetAllocatedBytesForCurrentThread() 是当前线程累计的托管分配字节计数，两个采样点之差回答“这段工作分配了多少”；要判断哪些对象仍可达，还需要查看引用和存活情况。线程分配计数也不会直接给出 GC 停顿时间。

固定输入与工作量 ​

下面两条路径都对整数 0 到 1023 求和。数组路径在测量区间内分配并填入元素，KeepAlive 保证该数组至少在指定调用点仍活着。计数前后的代码保持同步，输出放在采样区间之外。

csharp
using System;

static (long Sum, long Bytes) Measure(bool materialize)
{
    long start = GC.GetAllocatedBytesForCurrentThread();
    long sum = 0;
    if (materialize)
    {
        var data = new int[1024];
        for (int i = 0; i < data.Length; i++) data[i] = i;
        foreach (int value in data) sum += value;
        GC.KeepAlive(data);
    }
    else
    {
        for (int i = 0; i < 1024; i++) sum += i;
    }
    return (sum, GC.GetAllocatedBytesForCurrentThread() - start);
}

Measure(false);
Measure(true);
var loop = Measure(false);
var array = Measure(true);
if (loop.Sum != 523776 || array.Sum != loop.Sum) throw new Exception("different work");
Console.WriteLine($"sum={loop.Sum} loop={loop.Bytes} array={array.Bytes}");

将代码放入控制台 Program.cs，运行 dotnet run -c Release。两条路径都应得到 523776。数组路径包含一个可识别的托管数组，具体字节数受对象头、对齐和运行时实现影响；可以交换运行顺序并多次采样。把 Console.WriteLine 放到测量区间就会连格式化及输出的分配一起统计。

换个问题就换个测量 ​

若两次采样之间经过 await，延续可能在另一线程上执行，两个线程的累计计数相减没有所需含义。需要观察异步、并行工作时应选择覆盖整个目标进程和时间窗口的事件或计数器。若一直看见分配，却在工作结束及 GC 后没有持续增长的存活对象，仍可能是分配压力问题，不能据此定位泄漏。

自测：把数组保存到一个持续增长的集合，多次调用后，分配计数仍主要说明“产生过数组”。要证明它为何存活，还需观测 GC 后对象数或堆快照，并追查从根经集合到数组的引用路径。比较优化前后时先检查输入和总和，以免通过少做工作得到看似更低的成本。线程分配计数
