JavaScript 事件循环：任务、微任务与渲染机会 ​

点击事件、定时器和已完成 Promise 都可能使 JavaScript 再次执行。要预测先后，先标出哪些代码在当前调用栈上立即运行，再找出回调是由谁入队，以及入队的是任务还是微任务。ECMAScript 定义 Promise 的反应作业；浏览器的 HTML 事件循环安排任务、微任务检查点和渲染时机。

微任务检查点会消费新加入的微任务 ​

当浏览器执行一次微任务检查点时，会处理队列直到为空，包括处理中追加到队尾的微任务。queueMicrotask 直接安排回调，已兑现 Promise 上的 then 也安排后续反应。链上第二个 then 的处理器要等第一个处理器运行并确定其返回 Promise 的结果才会入队。因此，相邻写下的两个 then 可以被别的微任务隔开。

javascript
import assert from "node:assert/strict";

const order = [];
setTimeout(() => {
  order.push("timer");
  assert.deepEqual(order, ["sync", "one", "peer", "two", "timer"]);
}, 0);

Promise.resolve()
  .then(() => { order.push("one"); })
  .then(() => { order.push("two"); });
queueMicrotask(() => { order.push("peer"); });
order.push("sync");

在 .mjs 文件中执行 node 文件名.mjs。同步代码结束时，已排队的是 one 和 peer；执行 one 后，two 被追加在 peer 之后。此例只使用 Node 与浏览器共有的 Promise 和定时器语义。浏览器中的同一实验可以直接记录数组，在计时器回调里查看顺序。

让出执行权与让出渲染机会 ​

await 总会暂停当前异步函数；恢复时机取决于等待的结果。如果结果已经兑现，续体很快进入微任务队列。不断 await Promise.resolve() 的长循环仍可能占据整个微任务检查点，输入处理、计时器和渲染机会只能继续等待。把昂贵的同步循环包进 async 同样会在遇到第一个有效暂停点前占用执行线程。

把可拆分的计算安排到后续任务，让宿主有机会处理输入；需要真正并行时要考虑 Worker 和数据传递成本。requestAnimationFrame 在浏览器选择的渲染更新期间运行，适合协调视觉更新，回调中的长计算仍会推迟这一帧。setTimeout(fn, 0) 只让回调在符合条件后成为候选，不能保证立刻执行，更不能保证中间刚好绘制一帧。浏览器有不同任务来源，归属不同来源的任务没有全局先进先出顺序。

如何解释调度日志 ​

把第一段代码的 queueMicrotask 改为在 one 内注册，并保持第一段处理器正常返回。peer 和 two 谁先？再把一个零延时定时器和 Node 的 setImmediate 放在任意脚本的最外层，能否只凭上面的浏览器模型保证次序？

参考核对

在 one 内注册 peer 时，one 还没有返回；链上的 two 要等它返回后才入队，所以仍先看见 peer。Node 的 setImmediate 与计时器属于宿主不同阶段，顶层脚本里不能从这张微任务队列表推出固定相对次序。诊断应记录注册地点、回调开始与完成位置并区分宿主。HTML 事件循环与微任务检查点 · Node.js 事件循环与计时器
