C++ 构建排错：头文件、包发现、配置与规模 ​

前置：CMake目标和PUBLIC/PRIVATE用法要求。P2Report的库、CLI与安装后consumer见完整工程，诊断时分别画构建树与安装目标图。

示例未执行；下文现象与检查条件用于源码推演。

CMake库能编译但CLI找不到头文件怎么办 ​

CMake库能编译但CLI找不到头文件怎么办：先核对 p2_report 的 PUBLIC include 用法要求是否存在，以及 CLI 是否通过 target_link_libraries 链接目标。库自己的 PRIVATE 目录能让库编译，却不会把公共 include 传给 CLI；全局加 include 只会掩盖依赖图错误。

公共头路径应是 include/p2/report.hpp，源码 include <p2/report.hpp>；安装时安装 include/ 的内容到目标 includedir。大小写敏感文件系统会暴露 Windows 上未见的拼写问题。生成头漏生成则要检查 configure_file 位置与私有构建目录，不能把一个临时生成文件复制进源码树作为永久修复。

拿到真实错误时先保留编译器第一条找不到头的诊断和完整包含路径，再比较该目标的用法要求；本轮只提供诊断路径，不声称在任何编译器上重现。

find_package找不到P2ReportConfig怎么办 ​

find_package找不到P2ReportConfig怎么办：先看是否已安装，再定位安装前缀内真实的 Config 目录。CMAKE_PREFIX_PATH 是前缀列表，P2Report_DIR 应是包含 P2ReportConfig.cmake 的目录；把它们指向 include 或归档文件都无效。

若 Config 已找到但报告缺 P2::options，检查 export 集与 Config 的 Targets include 顺序；若编译通过但链接架构不匹配，则是包内容/工具链问题。若选错版本，检查缓存的 P2Report_DIR 与版本文件兼容政策。不要把缺包错误当成网络问题，本例不存在在线拉取依赖步骤。

重新配置一个空的 consumer 构建目录有助于区分旧缓存与包缺陷；不要求删除用户的现有目录。本轮未产生任何安装前缀，因而没有实际“查找成功”的日志。

CMake的Debug Release与多配置路径为什么混乱 ​

CMake的Debug Release与多配置路径为什么混乱：单配置 Ninja 在配置时读取 CMAKE_BUILD_TYPE，本例 out/debug 与 out/release 各自独立。多配置生成器通常在构建、CTest、安装时使用 --config/配置参数，并可能把程序放进 Debug 或 Release 子目录。

照搬单配置的 ./out/debug/p2-report.exe 到 Visual Studio 构建树，会把“找不到程序”误判为链接失败。更换生成器不能复用已有缓存。建议先确认 generator 与配置，再看真实产物位置，不用递归搜索任意旧 exe 运行来代替当前构建结果。

混用 Debug 与 Release 的 MSVC 运行库、迭代器调试设置或不同架构可能破坏 ABI。包版本1.x兼容声明不能消除这些差异；消费者与上游应明确同架构兼容工具链并记录实际版本。

大型CMake项目构建慢应该先检查什么 ​

大型CMake项目构建慢应该先检查什么：先用依赖图确认“改一个私有 cpp 却重编所有模块”是否来自公共头过重、全局选项变化或生成文件每次变化，再分别测量干净构建与增量构建。没有时间和受影响目标数据就不应声称拆库或并行一定加速。

库边界尽量稳定，公共头避免 include 实现细节；实现私有头不会向消费者传播目录。多核并行可缩短 CPU 空闲，但会增加内存压力；PCH、unity build、LTO 对吞吐、峰值内存和诊断有不同影响，需各自实验，不能当通用开关。

此完整工程刻意足够小以检查安装接口，不模拟几千翻译单元，也不伪造构建耗时。扩展至大仓库时沿相同 target 契约拆模块、以可复现输入比较更改前后的受影响目标与耗时，再决定优化。

练习与自检 ​

配置成功但消费者链接提示未定义 p2::summarize，应先检查哪三项？

参考答案与判断依据

先确认消费者链接的是 P2::report 而非只加头路径；再确认安装归档与头版本一致且 report.cpp 确实属于库源；最后确认 ABI/架构兼容及符号签名一致。配置成功只能证明生成规则，不证明归档内容或最终链接正确。
