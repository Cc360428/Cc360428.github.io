C POSIX 文件 I/O：短读写、错误与诊断 ​

描述符、短读写与错误契约 ​

考虑一份总共三个字节的普通文件。即使第一次 read 的缓冲区有 4096 字节，代码也只能消费返回值指定的字节数。先看指针和长度，再追踪扫描器中的 read/write 循环。

专题入口：C POSIX 文件接口：描述符、短读写与错误契约 · C POSIX 线程：创建、互斥与退出前收拢 · C POSIX 完整实践：双文件字节统计库 · C POSIX 排错：系统错误、死锁与不完整输出

C系统接口教学环境如何选择 ​

教学基线是 C11 和 POSIX.1-2008 已有接口。Windows 用户可在 WSL 的 Linux 发行版里运行该工程。项目用 CMake 3.20 及以上分离编译，实践页给出了 Linux 构建结果和输入规格。

前置是能区分指针与对象、知道循环和函数返回值；可先读内存与模块。本路径不是内核编程，也不覆盖网络事件循环。字节扫描器读取两个可信、有限、执行期间不变的普通文件；它不提供快照，也不用于安全打开任意设备。

C文件描述符由谁关闭 ​

open 成功返回非负整数，即进程描述符表中的一个入口；0 也是合法描述符，不能用 fd > 0 判断成功。失败为 -1。取得入口的 worker 必须在所有后续分支调用 close 一次，外部传给 report 的 stdout 则只是借用，库不能关闭。

描述符数值可能迅速复用；复制整数没有复制资源所有权。dup 产生另一个描述符，但可能共享底层打开文件描述与偏移。项目让每个 worker 独立 open 自己的路径，避免两个线程争抢同一个读取位置。路径被库复制，不借用 argv 的长期生存期。

C短读短写应该怎样循环 ​

read/write 返回 ssize_t，先判断正数、零、负数，再转换成 size_t。短读不是结束：返回3就累计3，下轮继续；只有 read 返回0才表示本次普通文件已到末尾。不能把未初始化的整个4096字节缓冲区都计入结果。

write_all 用 done 记录已提交前缀，每次从 data + done 写 length - done。-1 且 EINTR 时不前移偏移并重试；正数即使小于请求也先推进；零进展当 EIO 结束，避免忙循环。EAGAIN 需要就绪等待策略，不能照搬 EINTR 的立即重试。本项目的普通文件读和阻塞 stdout 不是通用非阻塞框架。

C的errno什么时候可以读取 ​

只在约定失败的返回值出现后立即保存 errno；成功调用可以留下以前的错误值，errno 非零不等于本次失败。清理、日志和其他库调用可能改变它，所以 worker 先把错误复制到自己的 error，再 close。

公开 scan_* 接口统一返回0或正的错误编号；调用者直接检查返回值，不读取线程局部 errno。pthread_create、pthread_join、mutex 系列本身也直接返回错误编号；不能用 perror 报告它们后再假定 errno 正确。把两种协议在包装层归一化，是跨语言错误处理的基础。

独立练习 ​

若 read 依次返回2、1、0，文件累计多少？write 依次返回2、-1/EINTR、3时，第二次和第三次请求应从哪里开始？为什么不能在成功后用 errno 决定是否失败？

参考解答与检查条件

读取共3字节；两次后续写都从偏移2开始，EINTR没有进度，第三次成功后偏移5。errno可能保留上一次调用的值，先检查返回值再取错误。

系统错误、死锁与不完整输出 ​

先读前节短读写与 errno 协议，再按路径、等待位置、输出信号及关闭策略排查。对照scan.c 与失败测试推演，本节没有故障实测记录。

C文件存在却open失败怎么查 ​

先记录实际工作目录与传入路径，再核对权限、父目录和链接目标。ENOENT 既可能是文件名错误，也可能是某一级路径不存在；不要在失败后随便把它解释成空文件。相对路径相对于进程工作目录，不相对于 scan.c 或可执行文件的位置。

库保留第一个有意义的错误，错误输出不暴露所有输入内容。本例不实现可信目录锚定或防恶意符号链接；若输入由不可信用户提供，需重新设计 openat 等目录边界，而非只加一次 exists 检查。

C线程程序挂住先检查什么 ​

先区分卡在文件读取、join 还是锁等待，再审查锁顺序。持锁 join 一个需要同一把锁的线程会永久互等；本例文件 I/O 在锁外，join 也在锁外，临界区只检查并更新 total。

这里要求输入是稳定有限普通文件，且不支持取消和超时。O_NONBLOCK 能避免 FIFO 常规等待，不能保证任意设备打开安全；fstat 的类型检查发生在打开之后。不应据此宣称可扫描任意恶意路径。必要时在隔离环境中观测线程栈，不能靠 sleep 让竞态“消失”。

C报告少了一截或者出现EPIPE怎么办 ​

输出目标关闭时可能先产生 SIGPIPE，若宿主忽略该信号才会让 write 返回 EPIPE。本 CLI 在进程入口设置策略，C 库本身不偷偷修改全局信号处理；嵌入别的应用时策略由那个应用决定。

短写必须从未写前缀后继续；失败时已写出的字节不能撤回，write_all 不提供事务发布或持久化保证。若要求保存完整报告，应另行设计同目录临时文件与替换协议，而不是声称循环 write 本身原子。

C关闭文件报错能不能直接重试 ​

close 报错的诊断不能覆盖更早 read 错误；本例只在此前无错时保留关闭错误。不能跨平台无条件重试 close：描述符可能已被释放并由其他线程复用，再次关闭可能伤及别的资源。

Linux 与不同 POSIX 版本/实现对于 close 被 EINTR 中断的资源状态存在差异；本例不承诺这种情况下跨平台绝无描述符泄漏。它选择不冒重复关闭的风险并返回失败；真实长期运行库必须针对选定平台制定关闭策略。普通文件读取项目不是通用取消安全库。

独立练习 ​

说明 errno、错误编号、信号退出三者如何区分。若第一个read失败且close也失败，应该报告哪个？

参考解答与检查条件

read失败取errno，pthread直接返回错误编号；SIGPIPE默认可能终止进程而没有正常write错误返回。保留第一个read错误，关闭失败不能抹掉根因；另需记录平台关闭策略。
