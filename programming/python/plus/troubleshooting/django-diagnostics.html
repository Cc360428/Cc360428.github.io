Django常见故障的定位顺序 ​

诊断对象是个人任务板完整工程；先能识别tasks/urls.py、settings.py中的SQLite路径和带CSRF令牌的POST表单，再按症状定位。

这个例子使用 Django 5.2.18。记录请求方法、命名路由、登录状态和测试数据库路径，可以将同一个 HTTP 状态对应到具体的响应阶段。

Django表单提交403怎样排查CSRF ​

遇到 403 先区分 CSRF 拒绝与权限逻辑：检查响应原因及服务日志，再确认 CSRF 中间件、POST 表单内隐藏字段、浏览器 Cookie 和同源地址。登录可能更新 CSRF secret，旧标签页表单应刷新再提交。不能以删除中间件作为修复。

HTTPS 反向代理环境还需核对外部 scheme、Host、Origin 与代理信任配置，不能无条件信任客户端提供的转发头。示例仅回环 HTTP，本轮没有代理或 HTTPS 实验。真实浏览器联调与部署 Cookie 策略仍待单独验证。

Django出现no such table应该检查什么 ​

no such table: tasks_task 首先检查迁移是否存在并应用，再检查当前设置与数据库路径。最常见的误判是给另一个环境运行了迁移，当前进程却读取不同 SQLite 文件。不要为了消除错误先手动建表，手动建表会绕开迁移历史。

用 showmigrations 查看已应用状态、migrate --plan 查看计划，并核对 BASE_DIR 指向的文件；新环境初次 migrate 还会建立 auth/session 等内置表。仓库提供手写初始迁移，其有效性需要框架的漂移检查与真实迁移验证。本例已经在临时 SQLite 文件上验证了模型无迁移漂移，并从空库执行迁移。

Django的NoReverseMatch和模板缺失怎样区分 ​

NoReverseMatch 表示命名空间、名称或参数无法反向匹配，检查 tasks:edit 是否提供整数 pk；TemplateDoesNotExist 表示模板路径未被加载器找到，检查 TEMPLATES 的 DIRS、APP_DIRS 和大小写。两类错误发生在不同步骤，不应通过硬编码所有地址一起“修复”。

本例项目级模板放 templates/tasks 和 templates/registration，login 默认寻找 registration/login.html。模板中的 URL 名称逐项对应应用 urls.py；测试调用 reverse 可在未来真实测试时进一步发现漂移。静态文件名存在不能证明完整模板渲染成功。

Django重复标题和database is locked怎样处理 ​

重复标题违反唯一约束，应回滚并向用户显示表单错误；database is locked 更可能是 SQLite 写锁争用或事务持续过久，两者不能统一当成输入重复。先收集异常类型、操作、事务范围、并发量和数据库后端，再决定缩短事务、排查长连接或选择服务型数据库。

本例只把 IntegrityError 转成保存冲突提示，不吞掉 OperationalError；未来生产日志应保留异常上下文而避免记录密码、会话 Cookie。切换数据库后必须重新验证大小写唯一性、迁移、并发写和事务测试，不能把 SQLite 的本地结果直接推广。

按症状寻找最短证据链 ​

症状首先区分最小核对点
无法启动且缺少DJANGO_SECRET_KEY配置输入问题当前终端进程是否设置变量；示例不会读.env
首页反复跳转登录会话未保留或用户未认证Cookie、域名、session表、登录重定向目标
新增后列表没有对象owner或state筛选当前用户、done值、筛选参数，检查是否真的成功保存
200但数据库没新增表单错误页面字段错误和非字段错误，不只看HTTP状态
404编辑地址路由不匹配或授权过滤命名路由、整数pk、当前owner；不要对外泄露归属
405退出/删除GET访问写操作使用带token的POST表单

定位时先记方法、路径、用户身份是否存在、表单错误和异常类型，避免把整个请求体、Cookie或密码写入日志。对于重复标题，可以记录约束相关的业务事件；对于数据库锁，需要记录事务时长和并发背景，不能不断重试掩盖根因。

静态检查和真实验证分别能说明什么 ​

若路由或模板出错，先以 reverse 检查命名路由，再让测试客户端请求页面并断言渲染内容。只检查模板文件存在不能发现反向路由参数拼错；只检查 HTML 标签配对也不能发现视图没有提供所需上下文。

在临时数据库上，任务板的六个测试覆盖了登录、对象归属、表单数据、方法限制和 CSRF 拒绝。若问题只出现在部署环境，再检查反向代理提供的 scheme、外部 Host、Cookie 属性以及数据库配置。
