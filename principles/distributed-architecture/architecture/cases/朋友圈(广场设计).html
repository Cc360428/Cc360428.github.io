朋友圈（广场设计） ​

这是一份历史设计草案，围绕文章、一级评论、二级回复和点赞说明数据关系。表结构与 Go 片段保留原稿；未完整声明的类型、字段和拼写属于伪结构，不能直接编译。先看点赞与计数规则，再对照下方 DDL；评论归属与分页见读取边界。

点赞 ​

创建点赞表设计 ​

mysql
CREATE TABLE `t_like` (
  `id` bigint(20) NOT NULL AUTO_INCREMENT,-- 表ID
  `statistics_id` bigint(20) NOT NULL, --文章ID
  `user_id` bigint(20) NOT NULL DEFAULT '0', --点赞人ID
  `create_time` datetime NOT NULL,
  `update_time` datetime NOT NULL,
  PRIMARY KEY (`id`) USING BTREE,
  UNIQUE KEY `user_id` (`user_id`,`statistics_id`) USING BTREE
) ENGINE=InnoDB AUTO_INCREMENT=3 DEFAULT CHARSET=utf8 ROW_FORMAT=DYNAMIC;
go
Id         int64       `json:"id"`                                 //ID
Statistics *Statistics `json:"statistics"`                      //喜欢的信息
UserId     int64       `json:"user_id"`                                //喜欢人
CreateTime time.Time   ` json:"create_time"` //添加时间
UpdateTime time.Time   `json:"update_time"`     //修改时间
  • 对 (user_id, statistics_id) 设置联合唯一索引，防止同一用户重复点赞同一文章。
  • 插入前仍须检查用户身份、文章存在性与访问权限；唯一索引只负责去重。
  • 仅当本次确实新增点赞记录时，文章点赞数才加一；重复请求返回已点赞状态，不重复加数。
  • 取消点赞也只在实际删除记录时减一；记录和计数在同一数据库时应在同一事务内更新。

点赞唯一性与计数一致性 ​

联合唯一索引解决的是同一用户对同一文章重复建记录，不能替代文章存在、可见性和用户权限检查。并发两次点赞时，只有实际插入成功的一次才增加计数；取消点赞也只有实际删掉记录时才能减一。若记录与计数在同一数据库，可在同一事务内更新；若计数异步投影，则要接受短暂延迟并具备按事实表重算能力。

去重检查与存在性、可见性检查分别承担不同职责。请求应表示“设为已点赞”或“设为未点赞”，避免把重试的 toggle 再翻回原状态。

文章与评论的读取边界 ​

文章、一级评论和二级回复分别有归属关系。读取二级回复时不能只按回复ID查询，还应验证它属于当前文章可见的评论树，避免绕过文章权限。原表保存昵称和头像属于快照还是缓存必须明确；若是发布时快照，改名后不自动变化不算错误。

分页可采用稳定的发布时间与ID复合游标，并明确删除项如何影响翻页；仅按时间排序会在同毫秒发布时产生不稳定顺序。评论计数必须决定只数一级还是所有回复，再用相同口径维护与重算。以下是逻辑归属图，不声明现有DDL已设置数据库外键。
