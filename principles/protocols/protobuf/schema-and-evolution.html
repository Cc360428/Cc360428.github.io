Protobuf消息、编码与兼容演进 ​

字段号、Wire类型与字段存在性 ​

前置：能阅读字段编号、整数位操作和 UTF-8 字节长度；Python 3.10+ 用于有限 wire 编码器，区别手写模型与生成代码。教学范围为proto3显式optional；二进制wire；Python3.10+手写有限编码器。核对日期2026-10-17。示例未执行，本轮没有安装依赖、生成协议代码、启动服务或浏览器预览。完整文件与输入见schema、编码器与字节推演；推演结论只适用于写明的模型。

字段号为什么不能复用 ​

字段号为什么不能复用：二进制数据携带线上标识而非字段名，改名未必改线格式，复用旧编号却可能把历史数据解释成另一含义。删除字段后保留编号与名称，不能为了让文件更整齐重新排号；类型变化也须按具体wire规则核对。

标签与wire类型 ​

标签与wire类型组合为字段号左移三位再加wire类型。字段1的uint32标签为8，采用变长整数；字段2的string标签为18，后接字节长度与UTF-8内容。wire类型只是编码类别，不足以推断完整业务类型或字段名。

缺省值与显式存在 ​

缺省值与显式存在影响PATCH等语义。proto3普通标量的缺省与显式零值通常无法仅凭值区分，optional可以保留是否提供的状态。消息类型和oneof也有存在语义；字段缺席不应被随意解释成删除或置零。

从字段定义到线上的标签 ​

字段号1与wire类型0组合为十进制8，即十六进制08；字段号2与wire类型2组合为18，即12。解码器先读取标签，再按wire规则取值，字段名要由schema解释。因此复用字段号即使还能解码，也可能把历史数据解释成错误业务含义。参见官方编码说明。

存在性是更新契约的一部分 ​

对可选年龄字段，未提供可以表示保持原值，显式提供0可以表示把年龄设为0；这只是一个可选的PATCH契约，必须由应用明文定义。读取字段默认值不能替代存在性检查，删除字段也不应通过复用编号实现。

集合字段、兼容演进与资源边界 ​

重复字段与映射 ​

重复字段与映射有不同契约。repeated保留元素顺序，map按键访问不承诺稳定遍历顺序；数字重复字段通常可打包编码。若签名或哈希依赖字节稳定，不能假定任意序列化输出都是唯一规范表示。

二进制兼容不等于JSON兼容 ​

二进制兼容不等于JSON兼容，因为ProtoJSON会用字段名称等文本表示。新增未知字段、枚举值和字段重命名都需核对读者行为；手工把消息逐字段拷贝到新对象可能丢失未知字段，不能把透传代理的兼容性只建立在schema上。

长度与资源边界 ​

长度与资源边界要求先验证长度前缀与剩余字节，发现截断即拒绝，再解码字符串，限制消息总大小防止资源消耗。本课有限解码器仅实现示例字段的wire0和wire2，不是完整protobuf实现，拒绝其他wire类型而不静默误读。

有限解码器必须先验证边界 ​

长度前缀只是发送方声明，不能相信它一定在剩余缓冲内。长度2而只剩1字节应立即拒绝；未知字段仅在支持其wire类型时按规则跳过。本课工具丢弃跳过的字段，作为转发代理时会丢信息，不能据此承诺无损演进。

业务验证边界与序列化选型 ​

schema不提供业务验证 ​

schema不提供业务验证：string允许空值，uint32允许零，只满足类型不能证明业务有效。应用仍需定义标题非空、ID合法范围与分配和访问权限。反之，解码错误通常是格式或兼容问题，不宜一律当成业务参数非法。

Protobuf与JSON选择 ​

Protobuf与JSON选择取决于读者、演进与调试需求。JSON字段名具有一定自描述能力、可读但仍需schema约束；protobuf紧凑但解读依赖契约，不能仅以“二进制快”断言端到端性能。数据大小、压缩、分配及消息结构都会影响结果。

Protobuf规范阅读 ​

Protobuf规范阅读固定proto3与wire编码指南，并用中文微软官方资料对照类型映射。新Editions有不同特性开关，不把两者默认行为混用。旧Go生成指南保留go_package与模块路径说明，本轮没有运行protoc或导入protobuf依赖。

解码成功之后仍要验证业务 ​

一个事件能被解码为event_id=0、title为空，并不代表它能进入事件系统。先区分字节结构错误，再检查字段值、字段间关系和调用权限；如果混成一个“解析失败”，排查时就无法知道是协议不兼容还是业务拒绝。

消息、字段存在性与兼容演进 ​

前置：Go 结构体与接口。Protobuf 定义跨语言消息，gRPC 使用服务定义生成调用代码；先学协议，再学生成器和网络调用。

最小协议 ​

保存为 api/hello.proto：

proto
syntax = "proto3";
package hello.v1;
option go_package = "example.com/hello/api;hellopb";

message HelloRequest {
  string name = 1;
  optional int32 age = 2;
  repeated string tags = 3;
}
message HelloReply { string message = 1; }
service Greeter {
  rpc SayHello(HelloRequest) returns (HelloReply);
}

package hello.v1 是协议命名空间；go_package 指定 Go 导入路径，可在分号后指定 Go 包名，二者不是同一个概念。路径应与模块和输出目录对应，不能用 ".;grpc" 代替完整导入路径来长期掩盖生成警告。

字段规则 ​

字段编号用于线上的二进制标识，名称改变不会自动改变旧数据的编号。已发布字段不能随意重用编号；删除字段后用 reserved 保留编号，必要时同时保留名称。不同字段类型之间也不是任意可安全替换。

proto3 普通标量字段不是 required，读取未设置字段通常得到默认值，不能仅凭这个值判断“调用方有没有提供”。需要区分缺省与显式零值时，按协议版本选择 optional、oneof 或其他明确表达。repeated 表示重复字段，map 表示映射；proto3 不支持给普通标量用 [default = ...] 自定义默认值。枚举第一个值必须是零值，通常命名为未指定状态。

Go 代码与生成器 ​

现代 Go 工具链分别使用 protoc-gen-go 生成消息、protoc-gen-go-grpc 生成服务代码。生成与 Go 包名排错流程见 gRPC 工程实践。不要手改生成文件来修复协议，应修改 .proto 与生成命令再重新生成。

生成的 Go API 会受 protoc、插件、运行时库和所选 API 模式影响，不能把某个历史版本字段布局当作所有版本保证。参见 proto3 语言指南 与 Go 代码生成指南。

练习与验收 ​

解释 name 为空字符串能否证明调用方未传 name；删除 age 时写出 reserved 声明；保持 go_package 导入路径与 go.mod 一致，再运行生成命令，确认消息与服务代码输出到 api 目录。

协议、生成代码与调用的关系 ​

协议是生成输入，消息代码负责类型和序列化，服务代码提供调用与服务端接口，实际业务处理仍由开发者实现。修改age编号后只重新编译代码并不能让历史数据安全迁移；需要先审查线格式兼容，再生成和测试。图示表示产物关系，不声称本轮运行过生成器。
