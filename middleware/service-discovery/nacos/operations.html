Nacos：排障、恢复与场景自检 ​

Nacos 配置与发现故障排查 ​

配置读不到 ​

Nacos 配置缺失 先核对 namespace ID、group、dataId 三元组，再看配置是否正式发布、应用是否命中 beta、是否读取本地快照。控制台显示名相同不代表 namespace ID 相同。getConfig 返回 null 与认证异常应分开处理：前者可表示对象不存在，后者不能当作“使用默认配置就好”，尤其涉及权限或安全配置时应按业务策略阻止启动。

读取内容还需验证格式和约束。配置中心保存文本不等于承诺业务语义有效；请求限制为负数应由应用拒绝，不应等事故发生后才回滚。保留有效配置版本、摘要与变更时间，有助区分发布、分发和应用接受三个阶段。

实例不可见 ​

Nacos 服务空集 排查依次统一 namespace、group、serviceName、cluster 与健康筛选；再查临时实例连接和客户端订阅缓存。持久实例仍存在不等于 healthy，临时实例短暂残留也不代表会话永远有效。业务地址 127.0.0.1 对其他主机表示它们自己，示例只供隔离阅读，不能复制为跨机注册方案。

注册返回后立刻发现空集可能是时序，不应无证据地改成持久实例或禁用健康过滤。应记录 SDK 版本、连接状态、注册目标和查询参数，并在授权实验环境观察；本轮没有执行这类观察。

鉴权与端口 ​

Nacos 鉴权失败 核对服务端是否启用相同插件、客户端 credentials 是否正确、token 是否过期、角色资源授权是否覆盖所需读写操作。不要把控制台可登录等同 SDK 被授权，也不要因为 namespace 存在就假设身份拥有权限。日志需隐藏密码、token 和签名密钥；用管理账号让示例“跑通”会掩盖权限缺口。

Nacos gRPC 端口 在 2.x SDK 链路中需与 HTTP serverAddr 和部署映射一起检查。默认主端口 8848 时客户端 gRPC 通常为 9848；自定义主端口、代理、容器映射和集群拓扑都会影响实际路径，不能把管理端口能访问当成全部端口正常。普通 HTTP 反向代理若没转发相应 gRPC 连接，也可能导致 UI 正常而 SDK 超时。

灰度回滚与升级 ​

Nacos 灰度回滚 先确认客户端实际拿到的内容与 beta 受众，再决定撤销灰度或发布一份经过校验的正式内容。回滚是新的一次发布操作，并不保证所有客户端同时切回；应验证业务生效状态，而不是只看控制台保存成功。客户端 IP 识别受代理/NAT 影响时，更需先核对受众身份，不能按浏览器本机 IP 猜测。

跨 2.x/3.x 升级应核对端口、SDK 兼容性、身份体系和客户端/管理 API 分离；本文的固定 2.4 示例不能用来证明 3.x 兼容。练习：UI 可用、SDK 超时、配置历史有更新，下一步是什么？参考解答：先确认协议与连接路径，再核对实际 namespace 和身份，不能重发配置覆盖历史来试错。

核对 2026-10-17，适用 2.4.x；依据官方 鉴权、SDK 与用于差异说明的 3.0 客户端接口。示例未执行，无实测排障结论。

Nacos 服务配置设计自检 ​

综合自检 ​

Nacos 综合自检 先分别画出配置链路和服务发现链路。配置从发布者写入指定三元组，到服务端保存与分发，再到应用解析、校验和替换；服务实例从注册、连接与健康维护，到客户端订阅快照，再到业务连接。二者有共同基础设施，也有独立状态，不能用其中一条成功证明另一条正常。

场景题与解答 ​

Nacos 命名自检：开发和生产有同名 reader.properties，应用却读错内容。参考答案应列出 namespace ID、group 和 dataId，核对实际客户端属性与摘要，再看 beta 分发及缓存。仅改文件名无法保证隔离，namespace 也不能代替授权。

Nacos 配置自检：发布接口返回成功，业务仍用旧值，是否直接再发布一次？参考答案：先确定客户端是否收到文本、解析是否失败、校验是否拒绝，以及是否仍保留上个有效对象。盲目重复发布会污染变更历史，不会修复应用解析器。灰度配置还应检查命中客户端范围，正式配置内容不能直接代表所有受众的实际内容。

Nacos 生命周期自检：断开客户端后希望实例仍存在，是否把 ephemeral 改成 false 即可解决一切？参考答案：这会改变生命周期和协议路径，却不能让已停止的业务变健康。持久实例需要明确的维护和删除策略；服务发现消费者仍应筛选健康实例并处理请求失败。

阶段设计与参考答案 ​

Nacos 设计复盘 作业是设计一次 request.limit 从 20 改为 30 的发布：先确定目标三元组和受众，再校验新文本、保留旧版本、检测并发编辑、选择灰度范围，最后观察应用实际接受结果。参考答案应说明 MD5 是内容摘要而非单调版本，灰度是配置分发不是流量调度，回滚是新发布而非时间倒流。动态更新必须先校验临时对象后原子替换，不能把坏文本覆盖到全局共享状态。

第二题：为什么本课程不提供将 2.4 curl 路径直接迁移到 3.x 的示例？参考答案：客户端、管理与控制台合同以及鉴权策略可能变化，应依据目标版本官方接口重新实现；固定 server/client 版本族是为了诚实限定可推导范围。仅修改版本号并不能证明协议兼容。

课程边界 ​

本课程交付 2.4.x 服务命名隔离、临时/持久实例、配置灰度、版本并发和鉴权理论，以及独立 Java 阅读项目。没有实现动态 listener、配置发布平台、跨机部署或 3.x 客户端，不声称覆盖这些能力。所有示例未执行，静态 XML 与模板检查不能证明 Maven 依赖兼容、SDK 编译、网络、权限或实际灰度行为。

核对日期 2026-10-17；一手来源 2.4 SDK、2.4 OpenAPI、3.0 客户端接口。没有旧文产品明确记为无旧文，不编造迁移来源。
