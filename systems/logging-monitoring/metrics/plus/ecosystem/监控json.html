Grafana API 与 MySQL 监控面板 JSON ​

本文保存两个独立的历史 Dashboard：API 的 schemaVersion 为 18，MySQL 为 16。先确认下面的依赖，再选择一份 JSON 导入；两段配置不能拼成一个 JSON 对象。

  • 准备：数据源与指标
  • 应用：选择并导入面板
  • 验证：从原始指标到图表
  • 常见问题：空图与统计口径
  • API 完整 JSON · MySQL 完整 JSON

准备：数据源与指标 ​

面板数据源与变量必须先核对的指标
API / Prometheus ServicePrometheus 类型的数据源变量 datasource；按 job、endpoint、method、status 筛选；interval 控制速率窗口，quantile 控制分位点service_uptime、service_http_request_count_total，请求/响应大小及耗时的 _sum、_count、_bucket
MySQL / MySQL 详细统计多处写死历史数据源名称 192.0.2.10:8836；host 来自 label_values(mysql_up, instance)，另有 intervalmysql_global_status_*、mysql_global_variables_*；内存对比还依赖 node_memory_MemTotal_bytes

这里的 IP:端口是导出时的数据源名称，不能据此推断当前 Prometheus 的访问地址。API 与 MySQL 的应用/Exporter 如何部署不在原记录中，应先在目标 Prometheus 确认指标存在。

MySQL 内存查询按 instance 联接数据库和节点指标。两类采集目标的标签必须能对应同一实例，否则即使两侧各有数据，比值面板也可能为空。旧版 MySQL、存储引擎或 Exporter 专属指标需逐项确认，不能要求每个目标都提供全部历史指标。

应用：选择并导入面板 ​

  1. 按目标下载下方 API 或 MySQL 的完整 JSON 文件，先在本地检查 JSON 能否解析，再导入目标 Grafana。
  2. 在目标 Grafana 的 Dashboard 导入入口上传该文件或粘贴 JSON。已有同 UID 面板时先确认是否覆盖；需要保留旧面板时另存副本。
  3. API 面板核对 datasource 变量；MySQL 面板逐项核对面板和变量中的历史数据源引用，再选择有效的 host。
  4. 先选一个有数据的 job/host 和明确时间范围，在副本验证后再保存用于日常观察。

完整导出保留旧 graph、singlestat 类型及原 UID、查询、布局。目标 Grafana 的版本和插件能力需在实际导入时确认；本文没有修改 schemaVersion 来伪装兼容。

验证：从原始指标到图表 ​

先在 Prometheus/Grafana 查询入口执行对应原始指标：

text
service_http_request_count_total
mysql_up
mysql_global_status_uptime
node_memory_MemTotal_bytes
  1. API：检查 job 和 endpoint 等标签确实有候选值，再观察 Requests QPS；有请求但为空时检查速率窗口内是否有足够采样。
  2. MySQL：先确认所选 host 的 mysql_up 与 uptime，再看查询速率、连接数和内存。单个面板为空时回到该面板的完整表达式核对指标和标签。
  3. 选择已知有请求/查询的时间窗口，对照应用或数据库侧的行为；“成功导入”只证明配置可读，不能证明采集链路和统计口径正确。

常见问题：空图与统计口径 ​

现象从配置能确定的排查点
API 的 endpoint 下拉缺少路径变量查询排除了 /metrics 和状态码 404；先检查查询过滤条件
API 请求/响应大小标题写 per second表达式是 rate(_sum) / rate(_count)，应按平均每次请求/响应大小理解，不能把标题当吞吐率
MySQL 所有图为空先检查历史数据源名称与 host 变量；再检查实际 Exporter 的指标名称
MySQL 仅内存比值为空对照 on(instance) 两侧标签和 node 指标，不要直接补零
旧面板类型无法显示在测试副本中检查目标 Grafana 的兼容/迁移提示，保留原导出用于对照
