核心心智模型 ​

Kubernetes 不是“运行容器的命令行工具”，而是一个持续协调期望状态与实际状态的分布式控制系统：

  1. 用户向 API Server 提交对象的期望状态。
  2. API Server 完成认证、鉴权、准入和持久化。
  3. 控制器观察对象并创建或更新下游对象。
  4. Scheduler 为未绑定的 Pod 选择节点。
  5. 节点上的 kubelet 通过容器运行时、网络和存储插件实现 Pod。
  6. 状态变化重新写回 API，控制循环持续收敛。

因此，生产操作应优先修改声明式配置并交给控制器收敛；直接改某个 Pod 通常只会得到暂时效果。

示例约定 ​

bash
# 明确当前上下文和命名空间，避免误操作
kubectl config current-context
kubectl config set-context --current --namespace=demo

# 只读命令可以先执行；写操作先做服务端 dry-run
kubectl apply --server-side --dry-run=server -f app.yaml
kubectl diff -f app.yaml
kubectl apply -f app.yaml
  • <pod>、<node>、<namespace> 是占位符，执行前必须替换。
  • 命令未写 -n 时，使用当前上下文的默认命名空间。
  • YAML 中镜像均固定版本；生产环境建议进一步固定镜像 digest。
  • kubectl run、kubectl create 适合调试或生成草稿，长期配置应进入 Git。
  • 文档中的云负载均衡器、CSI、CNI、Gateway API 等能力取决于集群发行版和已安装插件。

操作安全等级 ​

等级典型操作要求
只读get、describe、logs、top、auth can-i核对上下文和命名空间
可回滚写入apply、scale、rollout restart先 diff/dry-run，观察 rollout
高风险delete、drain、cordon、强制替换明确对象、影响窗口和恢复步骤
灾难级删除命名空间/PV、--force --grace-period=0、etcd 恢复变更审批、备份、双人复核、演练

不要复制即执行

执行任何写命令前，至少运行 kubectl config current-context、kubectl cluster-info 和目标对象的只读查询。生产集群不要依赖 shell 历史中的默认命名空间。
